# 从《Crafting Interpreters》边注看 Cyly 的设计取舍

本文按设计问题合并重复边注。每项说明它解决什么问题、收益、代价，以及放到 Cyly 中的判断。页码指 PDF 页码，`8.15` 这样的编号指译本中的边注编号。文中的代码只用于说明语义；函数、导入、指针等尚未确定的写法不是语法承诺。

**本文是评估文档。只有设计笔记里的内容属于已定决策。** 本文的建议不会自动增加语言特性，也不扩大第一版前端的实现范围。

## 1. 语言规范需要多精确，是否需要追求形式化

来源：1.3、11.1、12.22、28.18—28.20，PDF 第 3、22、25、48 页。

**说明。** 语言规范首先要让同一程序得到可预测的解释。例如，赋值是否产生值、同名声明是否允许、两个文件中的类型是不是同一个，都是用户会依赖的规则。把这些写清楚，不等于必须用证明助手证明整个类型系统，也不等于提供一套能表达任意数学命题的类型语言。

**好处。** 简短、具体的规则能指导实现和测试，避免编译器偶然的实现行为变成事实标准。保留“合法例子、非法例子、预期诊断”尤其适合 Cyly：比抽象口号更容易发现规则之间是否冲突。

**害处与代价。** 太早追求完备规范，会把大量时间花在尚无实际用途的组合上。反过来，完全不写语义，只照教程代码走，也会无意继承 Lox 的动态类型和运行时模型。

**对 Cyly 的判断。** 继续采用小规模、明确、能用例子检验的规则。已定的“不做推断、不做闭包”等边界本身就在减少证明和实现负担。边注中的历史趣闻、术语来源和形式系统介绍提供背景，不需要逐条变成语言议题。

## 2. AST、多阶段分析，还是边解析边生成代码

来源：2.5—2.11、5.3、5.8、11.9—11.11、17.15，PDF 第 4—5、9—10、23、30 页。

**说明。** AST 是程序结构的记录，例如“这个节点是加法，左右分别是什么”。后续可以依次确定名字指向哪个声明、表达式的类型、控制流，再生成代码。另一条路线是解析到一段语法就立刻生成指令，减少中间数据。

**好处。** 保留 AST 便于输出、诊断和后续静态检查，也允许先收集函数接口再检查函数体。各阶段可以有明确输入输出：解析阶段无需同时决定寄存器和栈布局。

**害处与代价。** AST 占内存，多次遍历耗编译时间，节点上的类型等信息还要有存放位置。把每一个小步骤都拆成独立框架也会增加代码量。直接生成代码更紧凑，却会使复杂类型、跨文件接口和错误恢复更容易纠缠。

**对 Cyly 的判断。** AST 输出已经是第一版目标，保留 AST 是自然选择。先有少量职责清楚的阶段，不必立即设计通用优化流水线。需要生成代码时再增加更低层的中间表示；中间表示简称 IR，可以理解为“更接近执行步骤的程序记录”。

## 3. 手写解析器、Pratt 解析和生成器

来源：1.6、6.5、6.8—6.12、6.17、17.2—17.10，PDF 第 3、11—13、29—30 页。

**说明。** 递归下降通常为语句或语法层级写函数；Pratt 解析用一张优先级表和前缀、后缀、中缀处理规则组织表达式。解析器生成器则读取文法，替人生成解析代码。这些主要是实现路线，不应改变用户看到的语法含义。

**好处。** 手写实现容易贴近 Cyly 的诊断需求；Pratt 对运算符、调用和成员选择的组合很方便。生成器能集中表达文法，适合规则较多、团队熟悉相关工具的项目。

**害处与代价。** Pratt 的结合优先级第一次阅读不如分层函数直观，表中一个数填错就可能改变整棵表达式树。生成器增加构建依赖和调试层次；手写解析器则需要自己维持文法一致性。

**对 Cyly 的判断。** 手写语句解析配合分层表达式或 Pratt 都可行，属于可以由实现者解决的选择。关键是用 AST 检验 `a + b * c`、`a = b = c` 和连续成员选择，不必让用户为解析算法选型。

## 4. 词法边界：字符、最长匹配、负号和字面量

来源：4.6、4.11、4.13—4.16、19.5，PDF 第 8—9、32 页。

**说明。** 词法器决定源码如何切成记号。最长匹配意味着看到一个可能的长运算符时优先识别它，而不是为了让后续语法合法而重新切分。负数可以被看作负号运算加数字字面量；字符串源码中的 `\n` 则需要解码成实际换行。

**好处。** 切分规则固定，词法器无需猜测上下文。把负号视为运算符，可以让 `-42` 和 `-x` 采用相同优先级。源码片段和解码后的值分开保存，有利于准确诊断。

**害处与代价。** `-2147483648` 需要特别处理：先把 `2147483648` 强行存进有符号 i32 会过早溢出。支持 Unicode 标识符还需要定义允许的字符及名称比较规则；允许字符串里有中文，并不自动要求标识符也支持中文。

**对 Cyly 的判断。** 现有 ASCII 标识符、原样保留源码、显式转义是清楚的起点。数值字面量可先保留原文或足够宽的幅值，到类型检查时再检查范围。`i32 x = 1` 中按目标类型检查字面量，不等于推断变量类型；但具体字面量规则仍需制定。

## 5. 优先级、结合性和合法赋值目标

来源：6.4、6.7、7.5、8.21—8.24、17.10、21.18，PDF 第 11、13、17、30、36 页。

**说明。** 优先级决定 `a + b * c` 如何分组，结合性决定连续相同优先级运算如何分组。赋值还需要区分“有一个值”和“能把值写进去的位置”：变量、可写字段可以是目标，`a + b` 通常不是。

**好处。** 固定规则便于阅读，也让解析结果稳定。先解析左侧表达式，再在遇到 `=` 时检查能否赋值，可以复用解析代码，同时精确报告“这里不能赋值”。

**害处与代价。** 运算符层级过多会增加记忆负担。Lox 禁止 `(a) = 3` 是其语言选择，不能当作所有语言的必然规则；保留或忽略括号节点，也应服从 Cyly 自己的规则。链式比较若直接左结合，可能产生用户不想要的含义。

**对 Cyly 的判断。** 右结合赋值已经确定，应得到 `a = (b = c)`。其他部分采用少量常规规则即可；不要添加可自定义优先级的运算符系统。字段、下标等赋值目标随对应能力加入，不必第一版一次补齐。

## 6. 错误诊断、恢复与源码位置

来源：4.6、4.11、6.15—6.16、8.22、17.7、18.11、24.24，PDF 第 8、13、17、29、31、40 页。

**说明。** 报错需要指出发生错误的文件、位置和原因；错误恢复则是在一个错误后继续寻找后面的独立问题。它不是把错误程序猜成正确程序。常见方法是跳到语句边界，或者专门识别常见错误写法。

**好处。** 一次编译可以发现多个问题。记录“文件编号、起始偏移、长度”能覆盖多文件，并避免每个节点都保存完整路径。需要展示时再转换成行列号即可。

**害处与代价。** 恢复过度会制造连锁误报；恢复时如果没有消耗输入，解析器可能死循环。只有行号不足以给出精确下划线，只有错误消息而没有原文范围也不够。中文和制表符还会让字节偏移与显示列数不同。

**对 Cyly 的判断。** 这是第一版已有要求，应优先做好。当前错误 token 的 `start` 指向错误文案，原文范围会丢失；后续宜把诊断和记号位置分开保存。先保证首个错误准确、恢复能前进，再增加针对常见错误的友好提示。

## 7. 条件是否只接受 bool，以及短路逻辑

来源：3.8、7.7、9.10—9.11、23.8—23.10，PDF 第 7、14、19、38 页。

**说明。** `if (x)` 可以要求 x 是布尔值，也可以规定零、空字符串、null 等哪些算“假”。逻辑短路则指：左边已经决定结果时，不执行右边。两者相关，但不是同一个选择。

**好处。** 只接受 bool，规则最少，也能发现把整数赋值误写进条件的情况；布尔赋值仍可能合法，所以这不等于禁止条件中的所有赋值。短路让“先检查、后使用”的代码自然成立，例如先确认联合成员，再读取该成员。

**害处与代价。** 严格 bool 会要求写 `count != 0`，比 C 式写法长。允许任意真值则必须记住每种类型的判断规则；若逻辑运算还能返回某个操作数，结果类型也会更复杂。

**对 Cyly 的判断。** 采用 bool 条件、布尔结果和明确短路，逻辑运算拼写为 `and/or`。Cyly 已决定支持位运算，具体运算符另行确定。联合类型中的 `null` 不自动等同于布尔假。

## 8. 数值转换、溢出与浮点行为

来源：6.7、7.11、7.16、18.18—18.19、30.11、30.19，PDF 第 11、14—15、32、51 页。

**说明。** 选择 i32、f32 之后，还要让有限位数的行为明确。整数超出范围时，可以回绕、报错，或让程序承担更强的前提。浮点会舍入，也可能有 NaN；因此数学上看似相同的式子在机器上未必相同。

**好处。** 固定基础运算能直接对应机器操作，无须用户定义运算符。明确转换规则可以兼顾常见写法和可预测性；需要特殊精度或检查时，用户可以调用专门函数。

**害处与代价。** 自动窄化可能悄悄丢失数据；每次检查溢出可能增加分支；允许编译器假定永不溢出则容易出现出乎用户预期的优化。浮点 `a <= b` 不能无条件改写为 `!(a > b)`：有 NaN 时两者不同。

**对 Cyly 的判断。** 已定的是“有固定内建运算和数值转换”，不是“完整照抄 C”。需要为常用整数和浮点选一套小而明确的规则。无论最后选哪套，常量计算、实际执行和优化器必须一致。LLVM 同样区分普通浮点运算与允许放宽语义的优化标记，不能默认混用。[LLVM 浮点说明](https://llvm.org/docs/LangRef.html#fast-math-flags)

## 9. 求值顺序，以及赋值表达式返回什么

来源：7.8、7.15、10.7、12.13、16.9、25.15，PDF 第 14—15、20、24、28、41 页。

**说明。** `f(next(), next())` 的两个调用先后顺序会改变参数值。对于 `items[index()] = makeValue()`，下标计算和右值计算也有可见先后。赋值作为表达式时，外层还会使用它产生的值。

**好处。** 规定从左到右，程序更容易读，测试也更稳定。赋值返回“实际存入后的值”，能让链式赋值在发生数值转换时有一致含义。

**害处与代价。** 固定顺序会限制部分重排，但不禁止编译器重排那些没有可观察差别的操作。返回转换前的右值虽然在部分实现里方便，却可能让 `a = b = x` 与“先给 b，再读取 b 给 a”不一样。

**对 Cyly 的判断。** 倾向明确求值顺序，并让赋值产生存入目标后的值。后者是建议，尚未写入决策。右结合只决定 AST 的分组，不能代替求值顺序的规定；两者应在实现语义时同时落实。

## 10. 语句、表达式、循环与语法糖

来源：3.3、3.7、3.10—3.11、8.1—8.2、9.5—9.17、23.1，PDF 第 6—7、15、19—20、37 页。

**说明。** `if` 可以只控制执行，也可以产生一个值；循环可以只提供 while，也可以增加 C 式 for、遍历序列的 for-in。语法糖是把更方便的写法翻译成已有操作，但翻译必须保持作用域和执行顺序。

**好处。** 少量常用语法能减少手写样板代码。C 式 for 直接表达初始化、条件和步进。范围或数组遍历也可以静态编译，不必天然引入动态迭代器和堆分配。

**害处与代价。** 每种形式都会增加解析、诊断和控制流规则。把 for 简单改写成 while 时，`continue` 必须仍然执行步进；否则所谓语法糖改变了行为。把所有语句都做成表达式，还会增加分支结果类型和作用域出口的规则。

**对 Cyly 的判断。** 第一版已有 if/else、while 足够。之后根据实际代码增加 for 等便利，无须为统一性把所有构造表达式化。要求花括号可减少悬空 else 等问题，但是否要求属于用户可见语法选择，仍是建议。

## 11. 作用域、初始化与声明前使用

来源：8.15、8.17、8.27—8.33、11.2—11.4、21.9、22.12，PDF 第 16—18、22—23、35、37 页。

**说明。** 一个名字指向谁、那个变量是否已经有值，是两个问题。词法作用域让名字由源码位置确定；初始化规则决定值什么时候可以读取。Lox 把无初始化的声明设为 nil，不能直接用于 `i32 x;`。

**好处。** 静态绑定可以把局部变量访问变为固定位置访问，无须每次按字符串查表。若支持“先声明、后赋值”，编译器可以检查所有到达读取处的路径都已赋值，避免运行时维护“是否初始化”的标记。

**害处与代价。** 确定赋值分析增加前端工作，也会保守地拒绝一些实际安全的程序。强制声明时初始化最简单，但有时迫使用户先写一个没有意义的占位值。默认零初始化也不是任意联合类型或资源对象的合理初始状态。

**对 Cyly 的判断。** 同作用域禁止重名、内层允许遮蔽已经确定。是否允许未初始化仍未定，不能从“不做类型推断”或“支持 null”推出答案。若允许，倾向静态拒绝未赋值读取；自引用初始化如 `i32 x = x;` 应有简单一致的名字规则，而不是运行时猜测。

## 12. 名字空间、前向引用与相互递归

来源：3.13、8.17、10.13、11.6、22.19，PDF 第 7、16、21、23、37 页。

**说明。** 名字空间决定变量、函数、类型是否可以同名。前向引用决定代码能否使用后面才写出的声明。先收集一个模块的类型和函数签名，再检查函数体，可以支持相互递归；这不要求先执行任何函数。

**好处。** 函数与变量共享值名字空间时，函数作为值容易理解。函数定义顺序自由，也减少 C 式重复声明。类型名字若与普通值明显区分，`Type name` 的解析和报错可能更直接。

**害处与代价。** 全部名字共用一个空间会增加命名冲突；分成多个空间又可能让同一个拼写指向不同东西。把局部变量也全部“提升”，会引入声明前读取和遮蔽的额外规则。收集声明也不意味着所有类型循环都合法：按值包含自身仍可能无法确定大小。

**对 Cyly 的判断。** 倾向函数和普通值共享空间，模块级函数先收集签名，局部变量按文本顺序处理。类型是否单独占空间值得结合 `Type name` 的实际文法决定。无需为了单遍编译而要求用户排列所有函数。

## 13. 语言类型、联合类型和机器表示

来源：18.1—18.8、22.19、27.6、30.9—30.18，PDF 第 31、37、45、51 页。

**说明。** 编译期类型规则与运行时表示是两个层面。Cyly 的类型名是透明别名，不产生独立身份；联合展开别名后合并重复成员。不同成员需要可查询的判别信息，但不要求保存用户起的类型名字。

```text
type Left = i32;
type Right = i32;
type Choice = Left | Right;
```

这里 `Left`、`Right` 和 `Choice` 都是 `i32`，不存在两个可区分的分支。同样，两个 `{ id: i32 }` 的别名在联合里会合并；需要区分用户与订单时，应使用 `{ kind: "user"; id: i32 }` 和 `{ kind: "order"; id: i32 }`。不同字面量描述了不同结构类型的取值约束，运行时身份不来自别名。

**好处。** 类型身份主要留在编译期，避免给每个普通值附加动态类型信息；联合的判别信息只在有需要的地方存在。固定字段对象也可以用偏移访问，无须运行时字段表。

**害处与代价。** 标签、对齐和最大成员大小会增加联合的占用；大型成员会抬高整个联合的大小。尝试压缩标签还会增加后端复杂度。匿名对象按结构兼容，也不自动规定字段的物理顺序：跨接口使用时必须采用一致布局或显式重排。

**对 Cyly 的判断。** 透明别名与联合去重是语言语义。`typeof` 查询联合当前成员；`readas` 按指定类型解释存储并读取，不检查当前成员，也允许成员不匹配的读取。这使存储表示对程序可见：标签编码、字段布局和跨类型读取结果需要一致的规则，不能借成员不匹配引入未定义行为。普通 `i32` 等值仍不必携带一套完整动态类型信息。

## 14. 类型收窄能消除什么成本

来源：2.4、11.6、22.19；结合联合类型议题，PDF 第 4、23、37 页。

**说明。** 收窄是根据控制流中已知的事实，在某段代码里把联合值当作某个成员使用。例如运行时判断它是否为整数分支，进入该分支后就可以使用整数操作。

**好处。** 编译器利用分支判断确认后续操作合法，随后生成对应成员的普通运算；无法确认合法的操作编译报错，不以自动插入运行时类型检查兜底。若编译期已经知道成员，分支判断也可能消失。

**害处与代价。** 值在判断后被修改，旧结论可能失效；通过指针或函数调用修改也可能发生。追踪一切别名关系成本很高。过于保守则需要用户重新判断，损失一些方便。

**当前决策（2026-11-09）。** 不做类型收窄，控制流不隐式改变静态类型。提供 `typeof` 查询联合当前成员，以及 `readas` 按允许类型解释存储并读取。`readas` 不检查当前成员，允许成员不匹配的读取；成员不匹配本身不属于未定义行为，编译器也不能假定匹配来优化。不提供共同字段的直接访问。常见场景的改写见 [联合查询与显式读取](UNION_ACCESS_EXAMPLES.md)；最终语法、具体存储表示和原地访问规则尚未由这些例子确定。

**历史检索。** [联合值访问与类型收窄](TYPE_NARROWING_OPTIONS.md)：记录此前的取值方式、分支稳定性、副作用约定等比较。

## 15. 函数值与匿名函数

来源：10.2—10.3、10.13—10.14、17.11、24.7、25.4，PDF 第 20—22、30、39—40 页。

**说明。** 函数作为值，意味着可以保存、传参或返回一个调用目标。匿名函数只是不给函数单独取名字；是否捕获外层变量，是另一项能力。函数类型写出参数和结果，便能在编译时检查调用。

```text
func(i32, i32) -> i32 operation = add;
```

这只是之前讨论过的写法示意，表达的是“operation 保存一个接收两个整数、返回整数的函数”。

**好处。** 排序比较、事件处理和算法选择可以用普通函数完成，无须建立类层次。无捕获函数值可以采用函数指针一类的目标表示，不需要捕获环境和相应堆分配。[Rust 函数指针文档](https://doc.rust-lang.org/reference/types/function-pointer.html)也将函数指针与捕获闭包区分。

**害处与代价。** 运行时选择目标时通常需要间接调用，内联也更困难。函数类型越复杂，声明越长。只支持模块级具名函数时，简短回调也需要单独命名。

**当前决策（2026-11-10）。** 支持函数指针，可存入变量、作为参数和返回值；函数参数类型与返回类型必须显式写出。普通函数只支持模块级具名定义，不支持局部函数、匿名函数或闭包，函数值不携带捕获环境。不支持普通函数同名重载。对象方法的内部定义和外部实现见第 19 条；原先支持无捕获匿名函数的建议不再适用，函数类型的最终语法另行确定。

## 16. 返回值、无返回值和可恢复错误

来源：8.2、8.7—8.8、10.20、18.9、25.17，PDF 第 15—16、22、31、41 页。

**说明。** 没有结果的函数可以有专门返回类型；有多个结果可以返回一个对象。错误则可以表现为普通返回数据，也可以通过异常跳到外层处理。编译器用什么办法实现 `return`，不等于 Cyly 必须提供同一种异常机制。

**好处。** 把可恢复错误放进返回值，控制流明显，和已有联合类型相配合。多个结果用具名或匿名对象即可，暂时不需要单独增加元组和多返回值规则。正常函数的参数、结果也能静态检查。

**害处与代价。** 显式检查和逐层传递错误比较啰嗦；异常能省掉这些代码，但需要规定传播、清理与跨语言边界的行为。Cyly 当前不做穷尽检查，因此返回一个错误联合，并不保证调用者一定处理了错误。

**返回值决策（2026-11-09）。** `void` 表示无返回值，与返回 `null` 区分。`void` 函数允许 `return;` 或正常执行到末尾，不允许返回值。有返回值的函数使用类型匹配的 `return 表达式;`；存在正常走到末尾而未返回值的路径时编译报错。

**异常处理决策（2026-11-09）。** 支持 `try` / `catch` / `throw`。函数可以用普通返回值表达失败，也可以通过异常传播失败；返回联合中的错误不会自动变成异常。捕获匹配规则、资源清理、异常存储和底层传播机制尚未确定。多个结果通过对象返回仍是建议。

## 17. 递归、尾调用与续延

来源：3.10、10.21、24.9—24.14、24.19，PDF 第 7、22、39 页。

**说明。** 普通递归让每次调用有各自的参数、局部变量和返回位置。尾调用优化可以在“调用完立即返回”时复用调用空间。续延则能保存并重新进入一段执行过程，会改变普通调用栈的生命周期。

**好处。** 递归非常适合树和语法处理，用常规调用栈即可实现。保证尾调用可以让某些递归程序使用固定空间。续延能表达复杂控制流程，但服务的需求明显更专门。

**害处与代价。** 递归深度可能耗尽栈；强制所有适用位置都消除尾调用，会约束调试、调用约定和资源清理。续延可能要求保存栈片段或改造栈帧表示，牵涉远超函数调用本身。

**当前决策（2026-11-09）。** 不提供续延。禁止尾调用优化，包括将尾递归转换为循环；尾部位置的调用按普通函数调用处理。`return f(...);` 仍是合法写法，普通递归和相互递归不受此限制。

**取舍。** 需要暂停和继续的任务，可以由用户显式保存状态，并通过函数或未来的方法推进；对象加状态机可以组织这些行为，但不会自动捕获任意调用链的执行现场，也不要求先引入完整 OOP。禁用尾调用优化会放弃相应的调用和栈空间收益，需要固定栈空间的迭代可显式写为循环。这项决定不等于禁止内联等其他优化，也不单独保证完整的物理调用栈。

**实现提示。** LLVM 提供阻止尾调用优化的 `notail` 标记；优化流水线也需落实禁止尾递归消除的要求。[LLVM 调用指令](https://llvm.org/docs/LangRef.html#call-instruction)、[尾递归消除](https://llvm.org/docs/Passes.html#tailcallelim-tail-call-elimination)。

## 18. 不做闭包意味着哪些便利也要放弃

来源：3.14、12.14、24.7、25.2—25.26、28.5—28.6、28.8，PDF 第 7、24、39—41、47 页。

**说明。** 闭包把调用目标和捕获数据绑在一起。显式写出捕获名单只说明捕获什么，仍要解决数据存放、复制、共享与寿命。把 `object.method` 保存成自动记住 object 的函数值，也会引入接收者环境。

**好处。** 闭包和绑定方法让回调很短，局部状态不用在多个参数之间传递。对于小型事件处理，这确实是很常用的便利。

**害处与代价。** 函数值会从单纯的目标变成“目标加数据”，调用、赋值、返回、保存都要遵守环境规则。即使某些闭包能放在栈上、无需分配，也不能因此省掉整套语义。

**对 Cyly 的判断。** 维持已定的“不做闭包，函数值不携带捕获环境”。需要状态时显式传入普通参数，生命周期由普通数据规则处理。普通点式方法调用仍可作为传入接收者的语法糖；自动生成绑定函数值则与当前方向冲突。能在编译期直接替换的常量，以及模块级名字的引用，可以不建立捕获环境；是否允许这些引用仍由名字解析规则决定。

## 19. 方法和封装是否必须依赖完整的类系统

来源：3.12、12.7、12.9—12.10、27.1、27.6、28.10，PDF 第 7、24、45、47 页。

**说明。** OOP 可以拆成数据组织、关联函数、访问权限、继承和动态分发。已有对象类型可以承担数据组织；`point.length()` 也可以在编译时改写为一个普通函数调用，把 point 作为参数。

**好处。** 关联函数改善名字组织和代码补全，静态调用不要求运行时查方法表。模块或类型层面的可见性还可以隐藏内部表示，独立于继承。

**害处与代价。** 即使方法只是语法糖，也要定义方法归属、名称冲突、接收者按值还是按引用。过多隐式接收者和自动转换，会让简单语法背后藏着难以预测的行为。全字段公开虽方便，却让调用方依赖内部细节。

**当前决策（2026-11-11）。** 允许在 `struct` 内部定义方法，支持私有方法；支持通过外部 `impl` 定义类型与方法对应的实现。父类通过外部 `impl` 定义的方法同样由子类继承，沿用类内方法的继承规则。`private` 仅用于变量和方法定义。子类重新实现继承方法必须写在子类定义内；外部 `impl` 只追加尚无实现的方法，不允许替换直接定义或继承得到的实现。同一类型与同一方法的重复直接实现报错，不以文件或加载顺序决定实现。

**对 Cyly 的判断。** 内部方法与外部 `impl` 可采用统一的实现表示，但允许的定义行为不同：覆写继承方法只允许在子类定义内进行。方法身份、调用选择、点式调用及对象身份仍需讨论。外部 `impl` 的私有访问权限留待多文件与模块设计时讨论，目前未采用具体授权规则。

**用户示例。** [用 impl 按类型或按操作组织代码](../examples/impl-organization.md)以圆、矩形的面积和周长对照类内集中定义与外部按操作定义，并展示父类外部方法的继承。

**补充评估：Visitor（2026-11-09）。** Visitor 将针对各类对象的一项操作集中到一个访问者中。预先建立访问协议后，新增操作通常只需新增访问者；经典 Visitor 新增对象种类时则需要扩充访问协议，并更新需要处理该种类的访问者。它调整的是代码按对象种类还是按操作组织，与类或原型的对象模型选择是不同维度。Cyly 已有的联合类型、普通函数和显式 `typeof` / `readas` 可以直接表达按操作组织的处理逻辑，不必为了这一需求引入类或 Visitor 专用语法；但不自动获得完整访问者接口所能提供的覆盖检查，误用 `readas` 的风险也仍由用户承担。类型种类固定、操作持续增加，与操作协议固定、实现种类持续增加，应当分别评估。[MIT 的 Visitor 讲解](https://web.mit.edu/6.102/www/sp25/classes/19-little-languages/#why_visitor)、[Zenger 与 Odersky 对两种扩展方向的分析](https://homepages.inf.ed.ac.uk/wadler/fool/program/final/10/10_Paper.pdf)。

**双向扩展的现有先例。** [Java、C++、Haskell、Zig、Rust 与 Lisp 对照](OOP_EXTENSION_PRECEDENTS.md)整理了类型外实现、行列组织、多投影编辑及自动转置的资料。Clojure 的 `extend-type` / `extend-protocol` 是两种组织方式共用同一机制的直接例子。Cyly 已选择类模型，见第 20 条。

## 20. 继承、原型与动态对象

来源：3.15、12.6、13.2—13.5、27.4—27.6、27.12、29.4、29.9，PDF 第 7、24—25、45—46、49 页。

**说明。** 继承可以复用实现，也常伴随“子类值可以当父类值用”。原型系统则让对象从另一个对象查找成员；动态对象还允许运行时增删字段。它们和“结构体有几个字段”不是同一个层面的能力。

**好处。** 继承适合某些成熟框架的扩展点；原型和动态字段适合运行时装配、脚本和交互修改。动态分发让调用方不必知道实际实现者。

**害处与代价。** 需要规则处理字段与方法冲突、覆写、父实现、对象布局和可变方法集合。动态查找可能增加间接访问或要求复杂优化。继承带来的子类型关系需要与 Cyly 已定的透明别名、结构兼容及联合类型规则协调。

**当前决策（2026-11-11）。** 对象模型采用类与继承，不采用原型模型。父类的类内方法与外部 `impl` 方法均参与继承。子类不允许删除继承的变量或方法；可以在自身定义内重新实现继承的方法，对继承变量的声明调整也只允许写在子类定义内。外部 `impl` 保持只追加、不替换已有实现的边界。

**仍需讨论。** 继承变量允许调整的具体内容（如初始值、类型）、方法覆写后的调用选择、多文件权限、对象身份和父子类型转换。限制调整发生的位置，并不自动允许任意改变变量类型。

**历史候选：通过删改派生定义（未采用）。** 曾讨论在新定义内删除方法、删除变量及改变变量类型，以编译期复用并修改已有定义。该方案需要在修改后重新检查保留代码，且不能仅凭来源关系保证结果可替代原类型。现已选择类模型，不再推进删除继承成员的方案。

**原型与子类的删除对照（2026-11-11）。** JavaScript 允许删除对象自己的可配置属性；对仅来自原型的成员执行 `delete child.member` 不会删除它，删除本地同名属性则可能使继承属性重新显露。直接删除原型自身的属性会影响依赖该原型的对象。[JavaScript `delete`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/delete)、[ECMAScript OrdinaryDelete](https://tc39.es/ecma262/multipage/ordinary-and-exotic-objects-behaviours.html#sec-ordinarydelete) Java、C++ 的通常继承规则不提供从派生对象中删去基类成员的操作；覆盖或隐藏不等于删除原成员。[Java 子类说明](https://docs.oracle.com/javase/tutorial/java/IandI/subclasses.html)、[C++ 派生类](https://eel.is/c++draft/class.derived)

Self 允许移除对象自己的 slot；其编程环境还提供 copy-down，可在复制结构时指定省略成员。手册给出 circleMorph 省略不需要的 rawBox 成员的例子。这是环境提供的结构复用机制，与语言中的父对象委托查找不同。[Self 手册](https://handbook.selflanguage.org/2024.1/howtoprg.html#copy-down)

这些先例说明不能笼统声称原型和子类都不允许删除。Cyly 随后选择类模型并保留继承成员集合；禁止删除继承成员是本项目的设计取舍，不是声称这种能力没有先例。

## 21. 同名重载、多方法和普通函数

来源：5.16—5.17、12.2、27.1，PDF 第 10、23、45 页。

**说明。** 重载通常按编译时参数类型挑选同名函数；多方法可以按多个参数的实际类型共同挑选实现。普通函数则通过名字直接指定行为。三者都能组织代码，但选择行为的位置不同。

**好处。** 重载能让相关操作使用统一名字。多方法对“形状与形状碰撞”等多对象组合比较自然，避免把所有组合都塞进某一个类里。

**害处与代价。** 同名候选、数值转换和联合类型组合后，需要规定“哪个更匹配”。动态多方法还可能需要运行时选择和方法注册。它并非在理论上一定无法静态检查或单独编译，但为这些能力付出的规则和实现工作会增加。

**当前决策（2026-11-11）。** 不支持按参数类型区分同名方法的重载；不同类型可以各自拥有同名方法。不支持多方法按多个参数的类型自动选择实现。普通函数和方法都使用清楚的名字，具体行为由调用者明确选择。

**对 Cyly 的判断。** 这保留了 `impl` 按类型或按操作组织代码的自由，又避免为候选匹配、联合类型和多参数分派增加一套规则。不做运算符自动派生，不等于逻辑上只能使用低级代码；用户仍可用普通函数表达需要的行为。

## 22. 初始化器、构造函数与失败

来源：12.21、27.8、28.11，PDF 第 25、45、47 页。

**说明。** 构造至少包含选择类型或联合成员、取得存储、填入字段，有时还需要打开文件等可能失败的操作。这些步骤可以由特殊构造语法完成，也可以由普通函数完成。

**好处。** 专门构造器能把初始化集中起来，并保证用户不会漏掉必要步骤。普通创建函数则可以自然地返回成功或失败，调用、测试和调试都沿用函数规则。

**害处与代价。** 特殊构造器若允许调用用户代码，就需要处理中途失败、部分初始化和资源清理。若字段允许任意外部修改，仅仅提供构造器也不能保证业务约束永久成立。

**当前决策（2026-11-11）。** 类可以定义显式 `init` 初始化函数；调用 `init` 仍属于变量声明中的显式初始化。`init` 可以使用默认参数，以一套初始化函数覆盖默认参数和特殊参数的创建方式；不通过多个同名 `init` 实现重载。变量本身不提供隐式初始化，类型声明也不自动派生默认值。

**对 Cyly 的判断。** 初始化函数解决私有字段、类不变量和父类部分初始化的组织问题，同时保留“变量必须写出初始化”的原则。具体的 `init` 语法、父类初始化写法、失败后的资源清理，以及对象按值还是按引用，仍需分别确定。不要把 `init` 的存在扩展成自动调用、构造函数重载或完整生命周期系统。

## 23. 值、引用、复制与相等

来源：7.2—7.3、18.19、20.14—20.20、27.12，PDF 第 13、32、34、46 页。

**说明。** 把一个对象赋给另一个变量，可以复制字段，也可以让两者引用同一份数据。比较对象可以比较内容，也可以比较是不是同一实例。这些选择会直接决定“修改一个变量后，另一个是否变化”。

**好处。** 值语义适合小记录，数据位置和复制成本直观；显式引用适合大型数据和共享修改。清楚区分内容相等与地址相同，能避免字符串驻留等实现优化改变程序含义。

**害处与代价。** 大对象复制可能昂贵，引用则引入别名和寿命问题。逐字段自动比较对资源、浮点或业务标识不一定合适。按原始内存做比较、计算哈希，也可能受到填充字节和表示差异影响。

**当前决策（2026-11-11）。** 沿用 C 式值语义：对象和结构体的赋值、按值传参复制对象值；指针是显式的，复制指针只复制地址，不自动复制指向的数据。不自动为对象提供内容相等运算，对象内容比较由用户逐字段或通过普通函数完成。`typeof` 只提供类型查询，不改变值、指针、赋值和传参语义。

**对 Cyly 的判断。** 类增加封装和继承，不因此变成默认引用对象或自动管理生命周期的语言。复制成本、共享修改和对象身份都保持可见；需要共享时使用指针，需要内容比较时写普通函数。具体的指针类型、可写权限、对象布局和父子对象复制规则仍需分别确定。

## 24. 字符串：长度、终止符、编码和拼接

来源：4.14、7.9、19.1、19.5—19.10，PDF 第 9、14、32—33 页。

**说明。** C 字符串用零字节结束；另一种表示显式保存地址和长度。后者能表达中间含零字节的数据，但还要决定它表示任意字节还是特定编码文本。字符串拼接则通常需要新的存储或可增长缓冲区。

**好处。** 长度明确，取字节长度无需扫描，切片也可以避免复制。保留终止符时，部分完整字符串能方便传给 C 接口。显式拼接函数或缓冲区让分配成本容易看见。

**害处与代价。** 地址加长度比单个地址多占空间；非结尾切片不能直接当 C 字符串使用。尾部有终止符也不能解决内部零字节让 C 接口提前结束的问题。UTF-8 的字节长度、码点数和用户看到的字符数不同，不能用一个“长度”含糊带过。

**当前决策（2026-11-14）。** 内建字符串类型是只读视图，由地址和字节长度组成，不依赖终止符，内容可以包含 `\0`。字符串是不解释编码的字节序列；长度表示字节数，下标若提供则取得单个字节。`==` / `!=` 按字节内容比较，不比较地址；不提供排序比较运算符。不提供 `+` 拼接、隐式转字符串和相邻字面量拼接；UTF-8 处理、拼接以及与 C 字符串的转换都留给库函数。

**对 Cyly 的判断。** 语言只承诺一个最小、成本可见的字符串表示；编码、分配和 C 互操作不进入语言核心。词法器已有的 `\0` 解码结果可由该表示完整保留。可写缓冲区、持有内存的字符串，以及下标是否做越界检查，分别留给内存管理（#27）和安全边界（#40）讨论。

## 25. 字符串驻留与哈希表

来源：20.1—20.21、26.16，PDF 第 33—35、43 页。

**说明。** 驻留是把相同文本合并成同一个内部条目。编译器经常反复比较变量名，因此可以先把名字转成编号，之后比较编号。哈希表用于从文本找到条目，但哈希相同仍需确认文本相同。

**好处。** 编译器名字比较更便宜，重复名字也能减少存储。开放定址等连续表结构可以减少指针跳转。把驻留限制在一次编译中，生命周期也比较好管理。

**害处与代价。** 驻留需要查表、保存文本和管理表本身；对只使用一次的字符串可能得不偿失。把运行时所有字符串永远留在全局表中，可能不断增加内存。哈希表的平均常数时间也不意味着最坏情况固定。

**当前决策（2026-11-14）。** 内容相同的字符串字面量在同一次链接的产物（一个可执行文件或一个动态库）内共用同一存储地址，跨动态库不保证；运行时不维护全局驻留表，用户在运行时构造的字符串不自动驻留。字符串 `==` 始终按内容比较，结果不依赖这项保证。不提供内建字典 / 哈希表类型和内建哈希运算，由库实现。

**对 Cyly 的判断。** 字面量合并由编译器按内容生成唯一符号、在链接时完成，不需要运行时成本。编译器内部是否驻留标识符属于实现选择，不进入语言规则。不做泛型时库容器的写法放到 #26 讨论。

## 26. 容器复用与不做泛型的实际代价

来源：15.11—15.18、20.3、20.14，PDF 第 27、33—34 页。

**说明。** 不同元素类型的数组会重复容量、扩容和追加等逻辑。泛型可以通过把一份带类型参数的实现展开成多种版本来实现复用；替代办法包括少量重复实现、代码生成，以及显式元素大小的原始存储接口。

**好处。** 泛型容器能同时保持类型检查和复用，不必每次通过无类型指针操作。另一方面，少量具体实现非常直观，语言和编译器都不需要处理泛型实例化。

**害处与代价。** 不做泛型确实会增加重复代码；原始存储接口则把类型正确性责任交给封装层。代码生成会增加工具步骤。泛型自身也会增加错误诊断、编译时间和可能的代码体积。

**对 Cyly 的判断。** 维持“当前不做泛型”。边注展示的是重复容器的一项真实代价，不足以证明泛型应成为所有代码的基础。等实际写出多个容器后再评估重复程度；有类型的内建数组也可以独立提供，不等于开放用户泛型。

## 27. 内存管理：手工、区域、引用计数和 GC

来源：3.6、19.12—19.13、26.2—26.23，PDF 第 6、33、42—44 页。

**说明。** 手工管理由程序决定释放；区域分配把一批对象集中分配、一起释放；引用计数在引用变化时更新计数；追踪 GC 从仍可访问的入口寻找活对象，再回收其余对象。它们解决的是寿命，不只是“调用一个 free”。

| 方式 | 主要好处 | 主要代价 |
|---|---|---|
| 手工管理 | 释放时间和数据布局可控 | 可能泄漏、重复释放或访问已释放内存 |
| 区域分配 | 分配简单，批量释放便宜 | 单个对象即使不用了，也可能要等整个区域结束 |
| 引用计数 | 引用归零时通常可及时释放 | 引用更新有成本，环需要额外处理，连续析构可能形成延迟 |
| 追踪 GC | 方便管理共享对象和引用环 | 需要识别活引用，耗时、占用和暂停需要权衡 |

**害处与代价的边界。** 不做闭包会减少需要逃逸的局部环境，但不会自动解决普通对象和指针的寿命。引用计数也不天然等于无停顿，GC 也不天然等于所有负载都慢。

**对 Cyly 的判断。** 倾向先围绕显式存储与生命周期设计，不把强制 GC 当默认运行环境；具体方式尚未确定。编译器本身很适合按文件或阶段使用区域分配，但这是编译器实现选择，不是 Cyly 用户程序的内存规范。若以后决定采用 GC，需要尽早设计根引用和外部接口，不能把它当作最后可随意插入的模块。

## 28. 多文件、模块、声明与定义

来源：3.13、5.16、8.17、20.5、28.4；结合最近的多文件讨论，PDF 第 7、10、16、33、47 页。

**说明。** 函数声明告诉调用方参数和返回类型，函数定义再提供实现。多文件需要确定引用路径、公开名字，以及哪些文件共享一个作用域。模块可以对应一个文件，也可以由多个文件组成，和库的二进制打包方式并非一一对应。

**好处。** 明确接口后，可以检查调用而不读取函数体。语言识别的导入能避免文本包含引起的重复定义、宏环境影响和手工同步声明。模块级命名也能避免全程序名字冲突。

**害处与代价。** 编译器需要管理依赖、接口和名字身份。文件即模块简单，但拆文件可能改变公开路径；多文件一个模块方便内部重构，却需要定义文件归属。C 式头文件便于发布文本接口，但要处理接口与实现不一致。

**对 Cyly 的判断。** 倾向显式导入、显式公开、由编译器识别接口。导入一个 `UserId` 应引用原声明的身份；在本模块写 `type UserId = other.UserId` 按现有规则会创建新类型，不能拿它冒充透明导入别名。模块系统需区分“引用已有名字”和“定义新类型”。这是前端语义，值得提前讨论。

## 29. 静态库、动态库、ABI 与 C 互操作

来源：10.10、24.21—24.26、28.4；库的具体设计是由这些边注延伸出的 Cyly 议题，PDF 第 21、39—40、47 页。

**说明。** 静态库通常把目标文件集合提供给链接器；动态库把部分代码保留为运行时依赖。ABI 是机器层接口约定，包括符号名、传参、返回值和数据布局。只有机器码，没有类型接口，一般不足以完成 Cyly 的静态检查。

**好处。** 静态链接便于把依赖代码打入产物；动态库支持独立分发和共享代码。明确 C 接口后，Cyly 可以使用现有库，也可以给其他语言提供功能。两种链接方式通常可以共享同一套源码调用接口。

**害处与代价。** 静态链接的库更新通常需要重新链接应用，多个产物也可能各带一份代码。动态库增加部署、加载路径和版本兼容问题。名字链接成功不代表签名和布局正确；通用 Cyly 联合不能未经约定就作为 C 的裸 union 传递。

**对 Cyly 的判断。** 可以提前确定导入声明、类型接口和显式 C 边界，目标文件和具体链接工作交给现成工具。早期不承诺任意编译器版本间的稳定 Cyly ABI，可先让同一构建使用一致接口。运行中主动加载、卸载插件是额外能力，不应随“支持动态库”一起默认承诺。

无闭包函数值有利于传 C 回调，但调用约定仍须匹配。回调状态宜由独立参数传递，不能把“无捕获”误当作“任意函数指针都能互换”。库返回的资源也应明确由谁释放。链接器负责组合目标文件和解析符号，[GNU ld 概述](https://sourceware.org/binutils/docs/ld/Overview.html)描述了这条职责边界；调用约定匹配见 [LLVM 调用约定](https://llvm.org/docs/LangRef.html#calling-conventions)。

## 30. 顶层执行、全局初始化、入口和 print

来源：4.2、8.3、8.9、8.17、10.11、21.16、24.4、24.25，PDF 第 8、16、21、36、39—40 页。

**说明。** 脚本可以从上到下执行顶层语句；系统语言也可以让顶层只放声明，从指定入口启动。一旦多文件顶层都有副作用，就需要决定谁先执行、导入是否触发执行，以及初始化失败怎么办。

**好处。** 顶层语句适合小脚本，`print` 语句能让早期前端示例简单。显式入口和初始化函数则使启动顺序可见，也方便把同一份代码用作库。

**害处与代价。** 隐式模块初始化会把依赖关系变成执行顺序；全局可变状态还会影响重用和并发。把 print 改成普通函数更统一，但在没有泛型、重载或格式化协议时，如何支持各种类型仍需一个明确方案。

**对 Cyly 的判断。** 保留第一版已经确定的 print 和当前基础示例。走到多文件和可执行程序时，倾向明确入口、显式处理有副作用的初始化。不要因为教程早期把顶层当脚本，就直接承诺所有模块导入时运行；也不要因为已有函数，就无条件认定打印可以完全由普通库函数替代。

## 31. 原生编译、生成 C、LLVM 与字节码

来源：2.5—2.17、15.7—15.8、16.13，PDF 第 4—6、26、28 页。

**说明。** 前端可以把程序交给不同执行路线：生成 C 再调用 C 编译器、生成 LLVM IR、自己生成机器码，或编成字节码交给虚拟机。`run` 命令也可以只是编译后立即执行，不需要另做解释器。

| 路线 | 主要好处 | 主要代价 |
|---|---|---|
| 生成 C | 借用现有平台支持和优化，产物容易检查 | 需要保护 Cyly 语义不被 C 的规则改变，调试映射较麻烦 |
| LLVM IR | 借用优化和多架构后端，可产出目标文件 | 依赖较大，需要理解 IR、目标布局和 ABI |
| 自写机器码后端 | 控制直接，构建链可以很小 | 每个平台都要处理指令、寄存器、目标文件和调试信息 |
| 字节码 VM | 指令集可控，移植解释循环相对容易 | 有指令分发成本；要接近原生性能通常还需更多工作 |

**对 Cyly 的判断。** 从接近 C 的成本目标看，原生产物值得优先。生成 C 和 LLVM 都是可行候选，当前无需拍板。若生成 C，应先把有副作用的实参按 Cyly 规则存入临时值，再调用，而不能直接依赖 C 实参求值顺序。LLVM 官方有[生成目标文件的完整示例](https://llvm.org/docs/tutorial/MyFirstLanguageFrontend/LangImpl08.html)，可作为后续实现参考。

## 32. 对象布局、对齐与零成本边界

来源：15.3—15.5、15.17、18.6、19.4、27.6，PDF 第 26—27、31—32、45 页。

**说明。** 对象大小不仅是字段大小相加，还可能包含对齐填充。布局影响数组占用、字段访问和函数传参。语言里的“对象”一词不要求每个对象都带类型指针，也不要求都在堆上。

**好处。** 普通固定字段对象可以接近 C 结构体的成本。具名整数等隔离包装通常可以只保留底层负载。把不参与执行的类型信息留在编译器里，符合未使用能力不收费的方向。

**害处与代价。** 一旦对外承诺稳定布局，重排字段或改变联合表示会受限制。选择自动装箱可以让传值大小统一，却增加间接访问和可能的分配。零成本也不能解释成任何高级写法都没有数据搬运或分支。

**对 Cyly 的判断。** 倾向固定布局、可理解的复制和显式间接。普通 Cyly 类型与 C 兼容布局可以分层考虑，不必所有类型从第一天就承诺跨版本二进制稳定。比较成本时，应与“手写相同功能的 C”比较，包括 C 里同样需要的标签、指针和检查。

## 33. 调试信息与执行数据分开保存

来源：4.6、15.22、17.7、18.11、22.17、24.2、24.24，PDF 第 8、27、29、31、37—40 页。

**说明。** 编译后的代码可能只剩槽位、地址和机器指令；要显示变量名、源文件行号和调用栈，需要额外映射。它们可以放在调试信息中，不必每次执行都携带完整名字对象。

**好处。** 保留可诊断性，同时避免让热路径反复处理字符串。源码位置从词法阶段一直传递，可以让错误落到实际运算符而非“最后读到的 token”。

**害处与代价。** 映射增加产物体积和生成工作。优化会合并、删除变量，调试器未必能展示每一步源码状态。只保留行号，在同一行有多个表达式时也不够精确。

**对 Cyly 的判断。** 第一版先让 token、AST 和诊断共享可靠源码范围。原生调试格式到生成代码时再做；不应为了减少运行时成本，把所有排错信息一起丢掉。

## 34. 编译器实例、源码寿命和全局状态

来源：8.33、16.1、22.6、22.10、29.6，PDF 第 18、28、36—37、49 页。

**说明。** token 指向源码内部，可以省掉文本复制，但源码必须活得足够久。若扫描器、错误列表等都存在进程全局变量里，就很难交错处理两个文件或同时运行两个编译任务。

**好处。** 一个显式编译上下文可以统一管理文件、诊断和内存。各文件自己的扫描器状态也方便导入时切换文件、写独立测试和以后接编辑器。

**害处与代价。** 参数和结构体数量会增加，需要清楚划分谁拥有内存。把每个小函数都塞进庞大“万能上下文”又会掩盖依赖，并不比全局变量好多少。

**对 Cyly 的判断。** 当前 `static Scanner scanner` 足以顺序扫描单文件，但未来宜改为显式状态。源码由编译任务保存到相关 AST 和诊断不再需要它为止，或者复制必要数据。这个改造属于编译器工程，不要求修改语言语法。

## 35. AST 表示、数据结构和实现限制

来源：5.9—5.19、11.6、15.11—15.18、17.5、20.3、24.19，PDF 第 10—11、23、27、29、33、39 页。

**说明。** C 实现可以用“节点种类加 union”表示 AST，再用普通函数分派处理。动态数组保存子节点，哈希表保存名字。每次增加节点需要更新解析、输出等操作，这是比采用某种设计模式更实际的维护问题。

**好处。** 少量显式结构容易检查，和现有 C 项目匹配。按倍数扩容使连续追加的平均成本可控。按阶段分配节点可减少单独释放的复杂度。

**害处与代价。** 不同操作里的分支可能漏掉新节点；生成代码可减少重复，却增加生成器维护。定长小数组和一字节索引容易制造教学示例之外的上限；无任何深度限制的递归解析又可能撑爆编译器栈。

**对 Cyly 的判断。** 优先直白实现，重复明显后才引入生成脚本。容量、索引和分配长度要检查溢出，资源不足应给出诊断。语法节点数量和嵌套深度的实际限制，应作为明确实现限制，而不是把教程里的 255 等数字直接变成语言哲学。

## 36. 基准测试究竟在测什么

来源：15.2、20.15、26.17、26.21、30.1—30.8、30.20，PDF 第 26、34、43—44、50、52 页。

**说明。** 编译器运行得快、编出的程序运行得快，是两件事。微基准能测调用或查表，真实项目能测编译时间、内存和整体体验。吞吐量表示单位时间完成多少工作，延迟表示一次操作要等多久，不能直接用一段执行时间的总和代替。

**好处。** 用实际负载比较，能判断某个复杂优化是否值得，也能发现“更快但多占很多内存”的交换。保留结果校验，避免测到错误程序或被优化器删空的程序。

**害处与代价。** 一个小基准很容易偏爱特定实现；调参迎合它，可能损害真实程序。debug 构建的热点也可能在优化构建中消失。测量本身需要稳定环境和足够重复。

**对 Cyly 的判断。** 将来用自己愿意写的命令行工具、文本处理和小型数据程序衡量。分别记录编译时间、运行时间、峰值内存、产物大小与启动体验。先保证行为正确，再测发布构建；不把“某次 Fibonacci 更快”当作语言整体更好的证据。

## 37. 优化不能偷偷改变语言含义

来源：6.7、18.18、28.17—28.18、30.14—30.19，PDF 第 11、32、48、51 页。

**说明。** 优化是换一种实现方式，保持程序允许观察到的行为。若允许改变浮点舍入、忽略 NaN 或假定某些指针不重叠，这些前提必须来自语言规则或用户明确选择。

**好处。** 稳定规则让优化器知道哪些变换合法。显式提供特定转换或低层操作，也可以让用户把需要的行为说清楚，避免普通表达式承担过多隐含机制。

**害处与代价。** 不受约束的内存重解释会限制优化；过强的别名假设又可能破坏用户认为正常的代码。NaN 装箱和指针打标能压缩动态值，但依赖表示约束，也增加可移植性和排错成本。

**对 Cyly 的判断。** 语义保证先行，优化后置。编译器用 C 实现时也不能随便通过不兼容指针读取同一块存储；[GCC 的严格别名说明](https://gcc.gnu.org/onlinedocs/gcc/Optimize-Options.html#index-fstrict-aliasing)区分了可接受与不可接受的写法。当前静态类型方向没有采用通用动态值的必要，NaN 装箱不值得优先投入。

## 38. 如果选择字节码，哪些技术才有意义

来源：15.17、16.6、17.5、18.15、22.15—22.16、23.3、23.8、28.4、28.13，PDF 第 27—29、32、37—38、47—48 页。

**说明。** 栈式字节码让指令默认操作栈顶，编码简单；寄存器式字节码显式指出输入输出位置，减少部分搬运。超级指令把常见连续指令合并，减少解释循环的分发次数。

**好处。** 这些技巧能改善 VM 的速度和代码密度。宽索引、长跳转可解除玩具实现的小上限。若允许加载外部字节码，验证指令边界和操作约束可以在执行前发现一部分损坏。

**害处与代价。** 指令越多，编译器、解释器和调试器需要同步维护的规则越多。更复杂的编码可能反而增加解码成本。验证格式正确也不等于任意程序都安全，更不等于已经实现沙箱。

**对 Cyly 的判断。** 这些是执行路线确定后的工程选择，当前不应为了教程覆盖面而提前实现。原生编译路线并不需要自己的字节码格式；自定义字节码也不天然等于通用、稳定的库分发格式。

## 39. 自举、REPL 与工具体验

来源：1.10、2.17、4.2—4.3、7.17、21.16，PDF 第 4、6、8、15、36 页。

**说明。** 自举是用 Cyly 编写 Cyly 编译器；REPL 则在同一会话里反复读入并执行代码。编译后直接运行的命令可以提供轻便体验，却不要求持久会话或解释器。

**好处。** 自举能检验语言是否真够自己使用；REPL 便于小实验；一个 `run` 命令可以省掉手工编译、寻找产物、执行的步骤。

**害处与代价。** 自举会让编译器错误和语言错误互相影响，还要维护启动编译链。REPL 需要处理会话状态、失败后清理和重定义；当前同作用域禁止重复声明，不能无意为 REPL 改成另一套语言规则。

**对 Cyly 的判断。** 先把文件编译和诊断做好，之后优先简单的编译并运行命令。自举留到语言足够稳定后检验实用性，REPL 则等确有需求再做。工具用起来顺手很有价值，但不必为此提前增加动态执行、热替换和顶层重定义。

## 40. 静态类型、内存安全与低层操作的边界

来源：7.12、18.4、30.14—30.18，PDF 第 14、31、51 页。

**说明。** 知道一个地址“应当指向整数”，并不代表那个地址仍然有效，也不代表下标没有越界。静态类型主要约束操作与值的类型关系；内存安全还涉及对象寿命、访问范围和实际存储。把一段比特按另一种类型读取，又不同于把一个数值转换成另一种数值类型。

**好处。** 提供显式指针和低层内存操作，便于调用 C、操作硬件或实现容器，用户可以自己控制检查和布局。将普通数值转换与比特重解释分开表达，也能让代码的意图更明确。

**害处与代价。** 默认提供无检查的访问，会把越界和悬空引用的责任交给用户；它们不一定立即报错，也可能破坏别的数据。默认检查下标，则可能增加比较和失败分支。若主要依靠静态规则保证寿命，需要更强的所有权或借用约束，也有学习和实现成本。

**对 Cyly 的判断。** 目前没有足够决策宣称 Cyly 是内存安全语言，也没有决定所有访问都不检查。比较合乎当前方向的候选是：普通类型错误尽量静态拒绝，低层操作明确表达，必要的检查由清楚的操作或接口提供。若以后提供 `unsafe` 一类标记，它只划出责任边界，本身不会验证内存正确性；是否需要这个语法，等指针与容器接口具体后再判断。

例如，访问一个“地址加长度”的视图时，检查范围只需要已有长度与下标比较，并不要求运行时类型系统或 GC。另一方面，关闭这次检查也不会顺便证明地址的寿命正确。把这些成本分开衡量，才能准确判断手写 C 会做什么、Cyly 是否增加了额外工作。

## 建议先讨论的顺序

1. **函数的基本契约。** 参数与返回类型、函数值、无返回值、求值顺序、递归。无闭包已经把范围缩小，适合下一步集中确定。
2. **对象和存储的基本契约。** 按值还是按引用、显式共享、字符串表示、谁负责释放，以及低层操作的检查边界。它们比类与原型的名称更影响成本。
3. **文件和接口。** 模块边界、公开名字、导入类型身份、入口与全局初始化，再往下确定 C 边界和库产物。
4. **继续实现最小前端。** AST、位置、恢复和明确的阶段；具体后端、字节码技巧和激进优化在有可运行程序后选择。

这里的顺序不是新增特性清单。已经决定不做的泛型、闭包、自动运算行为等，不需要因为原书涉及就重新立项。

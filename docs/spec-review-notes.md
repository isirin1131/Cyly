# A 组：可以从已定规则推出

## A1. 类不属于类型系统（原题"`class` 是名义类型"，提法有误，见条末修订）

**原问题（首轮第 4 条）。** 规范没有写 `class` 是名义类型还是结构类型。"对象类型"这个词同时用在 `typedef` 结构对象和类上，读者无法判断两个字段相同的类能否互相赋值。

**规范现状。**

- §3.1："`typedef` 结构对象按结构兼容；结构完全相同的对象类型之间可直接使用值。"
- §7.3："除结构完全相同的对象类型及第 4 章的联合构造外，类型之间不进行一般隐式转换；子类值到父类值也必须显式转换。"
- §11.1："`typedef` 结构对象不是 `class`。"

**例子。**（对象类型文法规范尚未给出，`{ value: f64 }` 只是示意。）

```cy
class Meters  { f64 value; }
class Seconds { f64 value; }
typedef Plain = { value: f64 };

func show(Meters m) -> void { print m.value; }

Seconds s = Seconds.init(1.0);
show(s);                 // 合法吗？
Plain p = s;             // 合法吗？
```

**推导。** 三条已定规则都指向"名义"：

1. 子类到父类尚且必须显式转换（§7.3）。如果两个毫不相干、只是字段碰巧相同的类可以隐式互通，就比有继承关系的类还宽松，说不通。
2. 类的 `{ ... }` 构造被限制在类自身内部（§11.6）。如果类与同结构的 `typedef` 对象兼容，外部就能先写一个 `typedef` 字面量再赋给类变量，这条限制形同虚设。
3. 方法按接收者的静态类型绑定（§11.5）。`Meters` 和 `Seconds` 可以各自有不同的 `describe` 方法；如果它们是同一个类型，绑定就没有依据。附录 B 也说过"不能仅因两个字段结构相同就宣称所有方法实现必须合并"。

**建议写进规范的内容。**

- 每个 `class` 声明创建一个独立的类型身份；两个类即使字段完全相同也是不同类型。
- 结构兼容只适用于 `typedef` 结构对象之间。类与 `typedef` 结构对象之间不兼容，也没有转换。
- §7.3 的"结构完全相同的对象类型"改为"结构完全相同的 `typedef` 结构对象类型"。

**后果。** 上例两处都是编译错误。`Meters | Seconds` 是有两个成员的联合，`typeof` 可以区分它们（§4.1 "同结构别名无法用 `typeof` 区分"只针对 `typedef` 对象）。

**决定：** [ ] 确认　[x] 另议：同意名义隔离。但类和类型是完全不同的概念，类型系统内部的概念绝对不能用来解释类。在 Cyly 中只有 class 的成员是 TypeName，没有反过来。类也不能用联合类型的 `|`

**修订（按上面的决定）。** 本条原来的提法是错的：问"类是名义类型还是结构类型"，本身就是拿类型系统的概念去套类。规范 §3.1 已经写了"`typedef` 结构对象与 `class` 对象分别遵守本章和第 11 章的规则"，两套规则互不解释。上面"后果"里的 `Meters | Seconds` 作废：类不能作联合成员。

本条改为下面的内容：

- 类不是类型系统的成员。结构兼容、透明别名、联合归一化、`typeof`、`.as()` 这些第 3、4 章的概念都不适用于类。
- 类的字段用类型来声明；反过来，类型表达式里不能出现类：类不能作联合成员。
- 两个类即使字段完全相同也互不相通；类与 `typedef` 结构对象之间不相通，也没有转换。

**规范里与此冲突的原文（已改）。** 这几处正是我读偏的来源，不改的话别的读者也会读偏：

1. §11.1："类是类型，类对象是该类型的值。"这句话直接说反了。
2. 文法用同一个 `TypeName` 既作 `TypeAtom`，又写类名：`"extends", TypeName`、`"impl", TypeName`、`ClassInitExpr = TypeName, ...`。应另立 `ClassName`，并说明它不是 `TypeAtom`。
3. §7.3："除结构完全相同的对象类型……外"，应写成"`typedef` 结构对象类型"。
4. §11.5："需要运行期多态时使用联合类型或显式函数指针。"类不能进联合，这里的联合指什么需要写明（见下面第 1 问）。

**边界的决定（已写入规范）。**

1. 指向类的指针是类型：`*Node`、`*Node | null`、`[4]*Node` 都合法。
2. 类对象的数组不允许：`[4]Node` 不合法，只能写 `[4]*Node`。
3. 类对象不能抛出或接收；要带类对象就抛指针。
4. 另立 `ClassName`。类名不是 `TypeName`，不能作 `TypeAtom`。
5. 变量、参数、返回值声明保留，文法改走 `DeclType = TypeExpr | ClassName`。函数指针签名 `*func(Circle) -> f64` 里也可以写类名。

**规范里有一处是我按你的话推的，你没有逐字说过，请确认：**

- **类的字段不能是类对象**，只能是 `*Node` 这样的指针。依据是你说的"只有 class 的成员是 TypeName"。`typedef` 结构对象的字段同样不能是类对象。

**这些决定带来的后果（规范里还没有写成例子）。**

1. 一个类不能按值包含另一个类的对象，组合只能靠指针或继承。连续存放一批类对象不能用数组，只能用一块内存加 `*Node` 下标。
2. 类对象没有"可空的值"：函数不能返回 `Node | null`，查找失败只能返回 `*Node | null` 或抛异常。
3. 抛出的指针指向谁需要作者保证：`throw &local;` 在栈展开后是悬空指针，被指对象必须放在 Arena 或模块变量里。
4. `typeof`、`.as()` 都不作用于类对象；运行期多态写成 `*Circle | *Rect`。
5. 文法上 `TypeName` 和 `ClassName` 都是标识符，语法分析阶段分不出来。`Node | null` 能通过语法分析，要到名字解析才报错。

**决定（字段不能是类对象）：** [x] 确认　[ ] 另议：

Cyly 错误定义的最佳实践基本上不会是 java 那种错误类型用 OOP 搞得很严谨的。而是用纯类型系统。

**处理。** 已写入规范（提交 `17d5d41`）。错误值用纯类型系统定义，所以上面后果 3（抛出的指针悬空）只是边角情况，不在规范里加例子。

## A2. `typeof` 只是一个比较形式，TBD 可以取消

**原问题（首轮第 6 条）。** 规范自己的例子 `typeof(value) == i32` 不被规范自己的文法接受：`i32` 是保留字，`Primary` 里没有"类型作为操作数"的产生式。`*Node`、`[4]i32` 这样的成员类型更没法出现在 `==` 右边。同时 §4.2 把"查询结果的静态类型、类型标识的底层表示、存储方式与开销模型"全部列为 TBD。

**规范现状。**

- §4.2："基础类型和自定义类型等类型系统标识符只作为 `typeof` 的返回值或比较目标使用，不允许作为变量存储或传递。这种查询不构成通用的第一类类型值或反射机制。"
- §7.2 文法：`Primary = ... | "typeof", "(", Identifier, ")"`，右操作数走普通表达式。

**例子。**

```cy
typedef Slot = i32 | *Node | [4]i32 | null;
Slot s = null;

if (typeof(s) == i32)    { }   // i32 是保留字，不是表达式
if (typeof(s) == *Node)  { }   // *Node 不是表达式（表达式里没有前缀 *）
if (typeof(s) == [4]i32) { }   // 会被当成数组字面量 [4] 后面跟 i32
```

**推导。** 类型标识既不能存进变量，也不能传参，那么 `typeof(x)` 的结果唯一能做的事就是立刻和一个写死在源码里的类型比较。也就是说，语言里实际存在的不是"`typeof` 运算加类型值"，而是一个整体的语法形式：

```
typeof(变量) == 类型
typeof(变量) != 类型
```

它的结果是 `bool`，运行时做的事情是"读联合的标签，和一个编译期常量比较"。

**建议写进规范的内容。**

- 文法在相等比较这一层增加专用产生式：`typeof "(" Identifier ")" ("==" | "!=") PrefixType`。右边按**类型**解析，不是表达式。
- 右边用 `PrefixType`（不含顶层 `|`），因为当前成员永远是单个成员类型。
- 变量的静态类型必须是联合；右边的类型必须是该联合归一化后的成员，否则编译错误（和 `.as()` 的检查一致）。
- `typeof(x)` 不能出现在其他任何位置；类型写在左边（`i32 == typeof(x)`）也不允许。
- 删除 §4.2 和附录 B 中关于"结果静态类型、底层表示、存储方式、开销模型"的 TBD。运行时开销就是联合本来就有的那个标签，没有额外的类型系统。

**后果。**

- `typeof` 不再需要任何运行时类型信息，"实现必须显式声明运行时开销"这句话可以改成"开销为一次标签比较"。
- 一个小的书写后果：`not typeof(x) == i32` 会被解析成 `(not typeof(x)) == i32` 而出错，因为一元运算优先级更高。要写 `typeof(x) != i32`，或者加括号。

**决定：** [ ] 确认　[x] 另议：typeof 的开销本来就预计为标签，那么 typeof(x) == typeof(y) 的表达式也应该被允许。

**处理。** 已写入规范 §4.2 与 §7.2：`typeof` 只出现在成员测试中，形式为 `typeof(place) ==/!= 类型` 和 `typeof(a) ==/!= typeof(b)`，结果为 `bool`，运行时动作是标签比较。「结果静态类型、开销模型」两项 TBD 已删除，只剩标签的编码与宽度待定。连带后果：`a`、`b` 属于不同联合时要能直接比较标签，这偏向 B3 的「全局类型标识」，留到 B3 决定。

## A3. 判空的写法是 `typeof(p) == null`

**原问题（首轮第 12 条之一）。** `T | null` 是语言唯一的可空形式，但规范没有说怎么判断一个值是不是 `null`。`==` 对联合没有定义，`typeof` 又只接受变量。

**规范现状。**

- §4.1："可空类型写作 `T | null`。"
- §4.2："参数只允许为变量……字面量、函数调用、字段访问及其他一般表达式均不能作为 `typeof` 参数。"

**例子。**

```cy
class Node {
    i32 id;
    *Node | null next;
}

func last_id(*Node head) -> i32 {
    *Node current = head;
    while (true) {
        // 想写：if (current.*.next == null) break;
        *Node | null next = current.*.next;     // 必须先复制到局部变量
        if (typeof(next) == null) break;
        current = next.as(*Node);
    }
    return current.*.id;
}
```

**推导。** `null` 是联合的一个成员类型，所以判空就是 A2 的标签测试：`typeof(p) == null`。字段、解引用结果、函数返回值都不是变量，必须先赋给一个局部变量再查。这是 §4.2 的直接结果。

**建议写进规范的内容。** 在 §4.2 加一个判空的例子，明说"对字段或函数返回值判空，需要先复制到局部变量"。

**后果（值得你看一眼）。**

1. 遍历链表这类代码每一步都多一个局部变量和一次联合值复制。如果你觉得太啰嗦，可以放宽 §4.2，允许 `typeof` 的参数是任意"存储位置"（变量、字段、下标、解引用）。这属于改动已定规则，我没有擅自建议。
2. `*T | null` 的大小是"标签 + 指针槽"，在 64 位平台上是 16 字节，是 C 里可空指针的两倍。链表节点里每个 `next` 都带一个标签。规范没有为"指针与 null 的联合"规定任何压缩表示。
3. 【新】作者也可以不用联合，直接用裸 `*T` 并以地址 0 作哨兵：`p == *Node(0)`。但指针之间能不能用 `==` 比较，规范还没写（属于规范自己列出的"基础运算的操作数与结果类型"待补项）。建议补写时明确指针支持 `==` 和 `!=`。

**决定：** [ ] 确认，保持"只接受变量"　[x] 放宽为任意存储位置　[ ] 另议：
当时的只允许变量，是因为我的前助手提议支持 typeof(i32) 这样的写法。

**处理。** 已写入规范 §4.2：参数是静态类型为联合的存储位置（变量、字段、下标、解引用）；函数调用结果等右值不行，`typeof(i32)` 不合法。上面例子里的中间变量 `next` 不再需要，可直接写 `typeof(current.*.next) == null`。后果 2、3（可空指针占 16 字节、指针能否用 `==`）未决。

## A4. "联合允许显式读取的类型"就是它的成员类型

**原问题（首轮第 12 条之二）。** §4.3 说 `.as(T)` 的目标"必须是该联合允许显式读取的类型"，但从未定义哪些类型算"允许"。

**规范现状。** §4.3 的例子里，`Number = i32 | f32`，`value.as(f32)` 和 `value.as(i32)` 合法，`value.as(string)` 是"错误：目标不被联合允许"。

**例子。**

```cy
typedef Number = i32 | f32;
Number v = 1;
i64 wide = v.as(i64);     // i64 不是成员，但比 i32 大，能读吗？
u32 bits = v.as(u32);     // u32 和 i32 一样大，能读吗？
```

**推导。** 规范的例子只有成员类型能读；`typeof` 返回的也是成员类型；"允许"一词没有别的来源。所以"允许显式读取的类型"就是联合归一化之后的成员类型集合，别无其他。

**建议写进规范的内容。** 把那句话改成"目标必须是该联合归一化后的成员类型之一"。

**后果。** 上例两行都是编译错误。想把存储按 `u32` 读，要先 `.as(i32)` 再做数值转换 `u32(...)`，或者走指针转换。

**决定：** [x] 确认　[ ] 另议：

这个毕竟是个很便宜的编译时特性，没理由不加。

**处理。** 已写入规范 §4.3：目标必须是联合归一化后的成员类型之一，同尺寸或更宽的非成员类型也不行。

## A5. 嵌套联合展平

**原问题（首轮第 12 条之三）。** 规范没有说联合的成员本身是联合时会怎样：是保留两层标签，还是合并成一层。

**规范现状。** §3.1："联合归一化合并重复成员；透明别名不能保留额外分支身份。"

**例子。**

```cy
typedef Number = i32 | f32;
typedef Value  = Number | string;      // 成员是 2 个还是 3 个？
typedef Same   = (i32 | f32) | string; // 和 Value 是同一类型吗？
```

**推导。** 别名是透明的，`Number | string` 展开就是 `(i32 | f32) | string`。如果保留两层，`Number` 就成了 `Value` 里一个有身份的分支，这正是"透明别名不能保留额外分支身份"所禁止的。所以只能展平：`Value` 的成员是 `i32`、`f32`、`string` 三个，只有一层标签。

**建议写进规范的内容。** 归一化步骤明文写出：展开别名；把作为成员出现的联合展平；合并重复成员。并说明展平只发生在联合的直接成员位置，`*(i32 | f32) | null` 的成员仍是 `*(i32 | f32)` 和 `null` 两个。

**后果。** 一个联合值的当前成员永远不是联合。`Value` 和 `Same` 是同一类型。但这**不**自动意味着 `Number` 类型的值能直接赋给 `Value`，那是 B3 要决定的事。

**决定：** [x] 确认　[ ] 另议：

**处理。** 已写入规范 §3.1：归一化三步（展开别名、展平直接成员、合并重复），并加了 `Value` / `Same` 的例子。

## A6. 期望类型是联合时，字面量按默认规则定型（有代价）

**原问题（首轮第 10 条之三）。** §3.2 说字面量在"具有明确期望数值类型的上下文中"定型为目标类型。当目标是联合时，规范没说怎么定型。

**规范现状。**

- §3.2："没有期望类型时，整数字面量默认定型为 `i32`，浮点字面量默认定型为 `f64`。"
- §4.2 的例子：`typedef Number = i32 | f32; Number value = 1;`。这里 `1` 进入了联合，说明规范认为它合法。
- §4.3 的例子和 `examples/unions.cy` 都**没有**写 `Number value = 1.0;`，而是先写 `f32 original = 1.0;` 再 `Number value = original;`。

**例子。**

```cy
i32 | f32  a = 1;      // 1 默认是 i32，i32 是成员 → 合法
i32 | f32  b = 1.0;    // 1.0 默认是 f64，f64 不是成员 → ？
i64 | null c = 1;      // 1 默认是 i32，i32 不是成员 → ？
u8  | null d = 200;    // 同上
```

**推导。** 联合不是"明确的数值类型"，所以字面量得不到期望类型，按默认规则定型：整数是 `i32`，浮点是 `f64`。然后做联合构造，要求定型后的类型是成员。规范和示例里绕着走的写法（先存进 `f32` 变量）也印证了这个读法。

**按推导的结果。** 上例 `a` 合法，`b`、`c`、`d` 都是编译错误，要写成 `f32(1.0)`、`i64(1)`、`u8(200)`。

**代价。** `i64 | null x = 1;` 和 `f32 | null r = 1.0;` 这类很自然的写法全部报错。只要联合里的数值成员不是 `i32` 或 `f64`，每个字面量都要套一层转换。

**另一个选择（不是推导，是新规则）。** 增加一条："期望类型是联合，且联合中恰好只有一个成员能容纳该字面量的种类（整数或浮点）时，字面量定型为那个成员。"这样 `b`、`c`、`d` 都合法；`i32 | i64 x = 1;` 因为有两个整数成员，仍按默认定型为 `i32`。

**我的倾向。** 这条规则不改变任何已经合法的程序的含义，只让更多程序合法，值得加。但它确实是新规则，所以交给你决定。

**决定：** [ ] 按推导，严格默认定型　[ ] 增加"唯一数值成员"规则　[x] 另议：尽量不做隐式规则。因此 1.0、1 等不能定为 f32、i32，字面量的具体规则应另讨论。

**处理。** 未改规范。并入字面量专题，与 B1、B4 一起讨论。

## A7. 模块变量可写；`ConstExpr` 用的是它的初始值

**原问题（首轮第 11 条之一）。** 规范没有说模块变量能不能被赋值。所有模块变量都必须用常量表达式初始化，又都能出现在别的常量表达式里，看起来像常量；但规范明确说不新增常量声明关键字。

**规范现状。**

- §3.3："已用常量表达式初始化的模块级常量值……是以 `ConstExpr` 初始化的模块级变量在编译期取得的值，不新增常量声明关键字。"
- §9.2："有副作用或运行时代价的全局初始化须在 `main` 或普通初始化函数中显式调用。"

**例子。**

```cy
i32 capacity = 16;
*Arena | null global_arena = null;

func main() -> void {
    Arena arena = arena_init(4096);
    global_arena = &arena;      // 运行时给模块变量赋值
    capacity = 32;              // 合法吗？
}
```

**推导。** §9.2 说全局状态的"真正初始化"要在 `main` 里显式做，这只有在模块变量可以被运行时赋值的前提下才有意义：先用常量占位，再在 `main` 里写入真实值。§3.3 的措辞"在编译期取得的值"也是在刻意区分"变量"和"它的初始值"。所以：模块变量是普通的可写变量；`ConstExpr` 里引用它时，取的是它的初始值，与运行时它变成了什么无关。

**建议写进规范的内容。** 在 §9.2 明说"模块变量可以在函数内被赋值"；在 §3.3 明说"`ConstExpr` 中出现的模块变量名表示其初始值"。

**后果。** 这个推导本身没有问题，但它直接引出 B2：一个既能当编译期常量、又能在运行时被改写的名字，在"常量下标越界检查""常量除零检查"里到底算不算常量。

**决定：** [ ] 确认　[x] 另议：本质上是迷糊助手的问题，当时我忘记了 const 这个东西。这个应该有很简单的解法。

**处理。** 未改规范，待确认。审阅者提出的方案：加 `const` 声明修饰符，`const` 名字必须用 `ConstExpr` 初始化且不可赋值，`ConstExpr` 里只能引用 `const` 名字，普通模块变量可写但不能进 `ConstExpr`；`const` 只修饰声明，不进入类型。若采纳，B2 的两个选项都不再需要。

## A8. 收窄字段的读取等同于 `.as()`，不是"类型保证"

**原问题（首轮第 15 条之一）。** §11.3 说字段收窄"在编译期提供静态类型保证"。这个保证不成立：通过父类指针可以合法地把槽写成收窄类型之外的值。

**规范现状。**

- §11.3："通过子类静态类型读取时，直接按收窄后的目标类型读取槽内数据，无需调用 `.as()`。""字段收窄在编译期提供静态类型保证。"
- §7.3.1：`*Parent(&child)` 是合法的零成本指针转换。
- §11.6 自己也承认父类 `init` 会写入"宽泛值"，要求子类覆写。
- 附录 B："规范不能通过'目标类型的不变量'重新引入这个被禁止的假设。"

**例子。**（类定义取自 §11.3。）

```cy
class Entity { string kind; i32 code; i32 | null value; }
class User extends Entity { "user" kind; 200 code; i32 value; }

func clear(*Entity e) -> void {
    e.*.value = null;            // 对 Entity 完全合法
}

func demo(User user) -> void {
    clear(*Entity(&user));       // 合法的指针转换
    print user.value;            // 静态类型是 i32，但槽里的标签是 null
}
```

**推导。** 语言在联合读取上的一贯立场是：`.as(T)` 不检查当前成员，读出来的是"按 `T` 解释槽里的字节"，编译器不得假设它一定匹配。收窄字段的读取就是编译器替你写了这个 `.as(T)`，立场必须一致。所以它提供的是"这个表达式的静态类型是 `i32`"，而不是"这个槽里一定是 `i32`"。

**建议写进规范的内容。**

- 把"提供静态类型保证"改为"确定该字段表达式的静态类型"。
- 明说：通过子类读取收窄字段，语义等同于对父类槽做 `.as(收窄类型)`；当前成员不匹配不是未定义行为，编译器不得假设匹配。

**后果。** 上例最后一行有确定结果：`null` 写入时整个槽被清零（§4.3 的尾部清零），所以按 `i32` 读出 `0`。对字面量类型的收窄字段（`"user" kind`），读出来是什么取决于 B4 的决定。

**决定：** [ ] 确认　[x] 另议：你是不是在钻牛角尖？你这个场景明显是父类变量赋值给子类变量才会出现的。

**处理。** 撤回。这个场景要先把子类对象的地址转成 `*Parent` 再写入父类的值，实质是父类的值进了子类对象，和其他指针误用一样由作者负责；附录 B 已禁止编译器利用这类假设，不需要新规则。

## A9. 方法的接收者只能按值；修改对象要用接收指针的普通函数（有代价）

**原问题（首轮第 16 条之一）。** 规范说修改外部对象"通过显式指针表达"，但没说具体怎么表达：是允许方法的接收者写成 `*Circle self`，还是只能写普通函数。

**规范现状。**

- §11.4："接收者显式写为首参数 `Circle self`，`circle.area()` 对应按值传入接收者的调用；需要修改外部对象时仍通过显式指针表达。"
- §11.5：类方法的函数指针类型"**统一为**以显式接收者 `self` 为首参数的普通函数指针 `*func(Circle, ...) -> ReturnType`"。
- 示例里所有会修改状态的操作都是普通函数：`arena_alloc_i32(&arena)`、`arena_deinit(&arena)`。

**例子。**

```cy
class Counter {
    i32 value;

    func bump(Counter self) -> void {
        self.value = self.value + 1;    // 改的是副本
    }
}

func bump_in_place(*Counter c) -> void {
    c.*.value = c.*.value + 1;          // 真正修改
}

Counter c = Counter.init(0);
c.bump();              // c.value 仍是 0
bump_in_place(&c);     // c.value 变成 1
```

**推导。** 方法指针的类型被"统一"规定为首参数是按值的 `Circle`，分派也只按接收者是哪个类的对象来定。规范里没有任何一处出现过指针接收者。所以按现有文字，方法的接收者只能是按值传入的类对象；要修改对象，只能写一个接收 `*Circle` 的普通模块级函数。示例的写法与此一致。

**代价。**

1. **每次方法调用都复制整个对象。** 一个 4 KB 的类，调用 `obj.checksum()` 就复制 4 KB。同样的事在 C 里会传指针。这和"成本接近手写 C"的目标有距离。
2. **修改操作不能是方法。** 它们不参与继承、不能被子类覆写、不能用 `super` 调用、不能用 `impl` 按列组织。动态数组的 `push`、Arena 的 `alloc` 都只能是 `vec_push(&v, x)` 这样的普通函数。
3. 类的方法因此只适合"只读、对象较小"的操作。

**另一个选择（新设计）。** 允许接收者写成 `*Circle self`，调用写作 `(&c).bump()` 或 `ptr.bump()`，分派依据"指针所指的类"。这样修改操作也能成为方法并参与继承。代价是要新增规则：指针接收者怎么调用、`.` 能否直接作用于指针（现在成员访问必须 `p.*.field`）、同一方法名能否同时有值接收者和指针接收者。

**我的倾向。** 推导的结果在规范内部是自洽的，和示例风格一致，改动最小。但第 1 点代价是实打实的，你应该明确知道后再确认。

**决定：** [ ] 确认，接收者只按值　[ ] 引入指针接收者　[x] 另议：为何不加入 self 关键字呢？OOP 的习惯值得我们写一些自洽小系统。但需另外细细讨论

**处理。** 未改规范。留给「`self` 与方法」专题，与 B6 一起讨论。

## A10. 调用继承来的方法时，传入的是父类前缀的副本

**原问题（首轮第 16 条之二）。** 子类对象调用没有被覆写的父类方法时，实际上发生了一次"子类值到父类值"的转换，而 §7.3 说这种转换必须显式写出。两条规则字面上矛盾。

**规范现状。**

- §7.3："子类值到父类值也必须显式转换。"
- §11.5："父类的方法……全局仅编译生成一份机器码；子类未重写该方法时直接复用父类函数实现。"

**例子。**

```cy
class Circle { f64 radius; }
impl Circle.area(Circle self) -> f64 { return 3.14 * self.radius * self.radius; }
impl Circle.describe(Circle self) -> f64 { return self.area(); }

class NamedCircle extends Circle {
    string name;
    func area(NamedCircle self) -> f64 { return 0.0; }   // 覆写
}

NamedCircle nc = NamedCircle.init(3.0, "x");
print nc.describe();    // 打印什么？
```

**推导。** `Circle.describe` 只有一份机器码，参数类型是按值的 `Circle`。`nc.describe()` 要调用它，只能把 `nc` 的前 `sizeof(Circle)` 字节复制过去，也就是做了一次 `Circle(nc)`。这是方法绑定规则的必然结果，不是一次"用户可以省略的转换"。

**建议写进规范的内容。**

- 在 §11.5 明说：接收者是子类对象、绑定到父类实现时，传入的接收者是该对象的父类前缀副本，效果等同 `Parent(obj)`；这是方法绑定的一部分，不属于 §7.3 禁止的隐式转换。
- 加上面这个例子，说明继承方法内部的 `self` 是父类对象，内部再调用其他方法时绑定的是父类实现。

**后果。** 上例打印的是 `Circle.area` 的结果（28.26），不是 `0.0`。`describe` 内部的 `self` 是 `Circle` 对象，`self.area()` 绑定到 `Circle.area`，子类的覆写不会被调到。这是"静态分派、没有虚表"的直接后果，规范应当用例子把它讲明白，否则来自其他语言的读者会默认它像虚函数一样工作。

**决定：** [ ] 确认　[x] 另议：你在找事？道歉。

**处理。** 撤回，审阅者道歉。方法绑定不是转换，与 §7.3 不冲突；§11.5 已写明「子类未重写时直接复用父类函数实现」「具体数据的来源不触发动态分派」，结论规范里都有。

## A11. 转换的目标类型可以收窄，文法歧义随之消失

**原问题（首轮第 7 条）。** `CastExpr = TypeExpr "(" Expr ")"` 把完整的类型表达式放进了表达式文法，产生真歧义。

**规范现状。**（A1 改动后 `CastExpr` 已写成 `DeclType, "(", Expr, ")"`，`DeclType` 仍包含完整的 `TypeExpr`，所以本条的歧义原样存在。）
- §7.2：`CastExpr` 是 `Primary`。
- §7.3.1：转换"只允许以下范围"：数值转换、指针转换、子类到父类的转换。

**例子。**

```cy
x = a | b(c);     // 读法一：把 c 转换成联合类型 a | b
                  // 读法二：a 按位或 b(c) 的调用结果
y = (f)(x);       // 读法一：把 x 转换成括号类型 (f)
                  // 读法二：调用括号表达式 (f)，参数 x
```

**推导。** 允许的转换目标只有三类：内建数值类型、指针类型、父类。联合类型、数组类型、括号类型都不是合法的转换目标。那么文法根本不需要接受完整的 `TypeExpr`：

- 数值转换的目标是内建数值类型名（保留字），或展开后是数值类型的 `typedef` 别名；
- 指针转换的目标以 `*` 开头，而表达式里没有前缀 `*`，所以不会和别的东西混淆；
- 父类转换的目标是一个类名。

**建议写进规范的内容。**

```ebnf
CastExpr = CastType, "(", Expr, ")";
CastType = NumericTypeName | "*", PointeeType | TypeName | ClassName;
```

`TypeName(expr)` 和 `ClassName(expr)` 在语法上和单参数函数调用相同，由名字解析区分（规范已经这么说了）。

**后果。** 上面两个例子都只剩读法二。没有任何合法程序因此变得写不出来。

**决定：** [ ] 确认　[x] 另议：理一下所有的转换规则，这个涉及基础类型、自定义类型和类，必须严格讨论。我倾向内建一个 x.to(T) 而不是沿用 C 的 T(x)

**处理。** 未改规范。留给「转换规则」专题：按基础类型、`typedef` 类型、类三类逐项列出 `.to()` 允许什么。

## A12. 声明与表达式语句：语言没有歧义，但要写明解析规则

**原问题（首轮第 8 条）。** 类型和表达式共用 `|`、`(`、`[`、标识符这些开头，解析器在语句开头无法用固定个数的前瞻判断这是声明还是表达式。首版目标恰好是"不带名字解析的语法分析"，所以这是首版就会撞上的问题。

**规范现状。** §8.1：`BlockItem = VariableDecl | Statement;`，`VariableDecl` 以 `TypeExpr` 开头，`ExprStmt` 以 `Expr` 开头，两者没有消歧说明。

**例子。**

```cy
A | B x = make();        // 声明：类型 A | B
a | b;                   // 表达式语句：按位或

(Value) n = make();      // 声明：括号类型（Value 是 typedef 别名）
(value);                 // 表达式语句

[3][4]i32 grid = fill(); // 声明：二维数组
[3][0];                  // 表达式语句：数组字面量 [3] 取下标 0

{ a: { print 1; } }      // 块，里面是具名块 a
{ a: 1 };                // 对象字面量作表达式语句？
```

**推导。** 仔细看，这些在**语言**层面其实都没有歧义：

1. 合法的表达式里，永远不会出现"一个完整的类型后面紧跟一个标识符"。`a | b x` 作为表达式是语法错误。所以只要能解析成 `TypeExpr Identifier`，它就只可能是声明。
2. 没有期望类型的对象字面量没有意义（它的类型无从确定，也没有副作用），所以语句开头的 `{` 没有理由解释成对象字面量。
3. `标识符 :` 开头的只能是具名结构。

缺的只是把这几条写成规则，让实现者知道怎么做。

**建议写进规范的内容。** 在 §8.1 增加消歧规则：

- 在允许声明的位置（块内、`for` 的初始化部分、模块顶层、类体），如果输入能解析为 `DeclType`（类型表达式或类名）后紧跟一个标识符，则它是声明；否则按表达式语句解析。
- 语句开头的 `{` 总是开始一个块。
- 语句开头的"标识符后紧跟 `:`"总是开始一个具名结构。

**后果。** 第一条规则意味着解析器需要试探性解析（先按类型试，失败再回退），或者等价的前瞻扫描。这对手写递归下降是可行的，但它不是简单的单 token 前瞻，规范应当明说，避免实现者以为自己写错了。

**决定：** [ ] 确认　[x] 另议：真会钻牛角尖啊，你得反省自己了。我记得已经禁止 (a) = 1，你应该知道我也想禁止 (i32) a = 1；而且明明命名我已经限定给块、循环和 if 了，你居然还在提

**处理。** 撤回本条的消歧规则。具名结构 §8 已限定给块、`if`、循环，不该再提；`A | B x = ...` 在语言层面没有歧义，是实现者的事。

按 §7.4 的同一原则写入了规范 §3.1：声明的类型不能整体是一个括号类型，`(i32) a = 1;` 不合法；括号作为更大类型的组成部分仍合法，如 `*(i32 | f32) p`、`(*func(i32) -> i32) | null cb`。审阅者一度把它概括成「声明不能以 `(` 开头」，这是错的：`(&a).* = 1` 合法，被禁止的只是括号本身充当赋值目标或声明类型。因此这条不影响 A13。

## A13. `*func(i32) -> i32 | null` 到底是什么（两条已定规则相互冲突）

**原问题（首轮第 9 条）。** 按文法，`| null` 被函数指针的返回类型吞掉，于是"可空的函数指针"没法直接写出来。

**规范现状。**

- §3.1："前缀 `*`、`[N]` 的结合优先级高于 `|`。因此 `*T | null` 表示指向 T 的指针与 null 的联合。"
- §10.1：`FunctionPointerType = "*", "func", "(", ..., ")", "->", ReturnType;`，而 `ReturnType = TypeExpr | "void"`，`TypeExpr` 包含 `|`。

**例子。**

```cy
*func(i32) -> i32 | null callback = null;
// 读法一：(*func(i32) -> i32) | null     可空的回调
// 读法二：*func(i32) -> (i32 | null)     返回可空整数的回调，此时 = null 是错误
```

**这条我要更正一下。** 上一轮我把它归为"可推出"，理由是"`*` 前缀高于 `|`"。写细之后我认为它其实是**两条已定规则的冲突**，需要你选：

- **选项一：`*` 前缀优先。** 函数指针类型里的返回类型不含顶层 `|`。`*func(i32) -> i32 | null` 是可空回调；返回联合要加括号：`*func(i32) -> (i32 | null)`。
  - 好处：和 `*T | null` 的规则完全一致；可空回调是常见需求，写起来最短。
  - 坏处：同样的文字 `-> i32 | null`，在函数**声明**里表示返回联合，在函数**指针类型**里却不是。
- **选项二：返回类型贪婪（即现有文法）。** `*func(i32) -> i32 | null` 是返回可空整数的回调；可空回调写成 `(*func(i32) -> i32) | null`。
  - 好处：`->` 后面的东西在声明和指针类型里含义一致；TypeScript 的函数类型也是这样。
  - 坏处：是 §3.1 那条规则的例外，需要在 §3.1 明说。

**我的倾向。** 选项一。§3.1 的规则是作为普遍原则陈述的，例外越少越好；而且写回调参数时，"可空"比"返回联合"常见得多。但两者都说得通。

**决定：** [ ] 选项一，`*` 前缀优先　[ ] 选项二，返回类型贪婪　[ ] 另议：

## B1. 字面量参与运算时怎么定型

**原问题（首轮第 10 条之一、之二）。** 现有定型规则只处理"单个字面量直接落在有期望类型的位置"这一种情况。字面量一旦带上负号或参与运算，规则就失效，而且失效得很难看：最小负数写不出来。

**规范现状。** §3.2：字面量在"变量声明初始化、赋值、函数传参、`return`，以及同类型二元运算中另一侧已经定型的情况"下定型为目标类型，超范围报错；否则默认 `i32` / `f64`。§2.2："负号作为一元运算符处理。"

**例子。**

```cy
i8  a = -128;            // 128 超出 i8 → 错误。i8 的最小值写不出来
i32 b = -2147483648;     // 2147483648 超出 i32 → 错误。i32 的最小值也写不出来
i64 c = 1 << 40;         // 两个字面量都没有"另一侧已定型"→ 都是 i32 → 结果 i32 → 不能赋给 i64
i64 d = 1 + 2;           // 同理，i32 + i32 → 不能赋给 i64
f32 e = 1.0 / 2.0;       // f64 / f64 → 不能赋给 f32
f64 f = 2;               // 整数字面量进入浮点位置，允许吗？
f64 g = f * 2;           // 另一侧已定型为 f64，整数字面量 2 能定型为 f64 吗？
```

按现有文字，`a` 到 `e` 全部是编译错误。

**选项。**

- **选项一：未定型常量运算。** 字面量之间的运算结果仍然是"未定型常量"，在编译期按精确值计算，直到遇到期望类型或需要默认类型时才定型并检查范围。
  - `-128` 是值为 -128 的未定型常量，落进 `i8` 时合法。`1 << 40` 是未定型常量 1099511627776，落进 `i64` 合法，落进 `i32` 报超范围。
  - 这是 Go 的做法。它和规范已有的 `ConstExpr` 概念天然契合，编译器反正要做常量求值。
  - 要注意的坑：`f64 x = 1 / 2;` 里 `1 / 2` 是整数常量除法，结果是 0，然后变成 `0.0`。
- **选项二：期望类型向下传递。** 期望类型穿过运算符传给两个操作数。`i64 d = 1 + 2` 里两个字面量都按 `i64` 定型。
  - 解决了 `c`、`d`、`e`，但 `-128` 仍然不行（`128` 按 `i8` 定型就已经超范围），还得再加一条"负号加字面量视为一个整体"的特例。
- **选项三：只修负数。** 只规定"一元负号直接作用于数值字面量时，两者合起来作为一个字面量定型"。`c`、`d`、`e` 保持错误，要写 `i64(1) << 40`。

**关于整数字面量进入浮点位置（`f`、`g` 两行）。** 这是独立的子问题。§3.2 说字面量"定型为目标整数或浮点类型"，没说整数字面量能否定型为浮点。

- 允许：`f64 f = 2;` 合法，`x * 2`（`x` 是 `f64`）合法。要求该整数能被目标浮点类型精确表示。
- 不允许：必须写 `2.0`。规则更简单，代码稍啰嗦。
- 反方向（`i32 n = 1.0;`）我建议一律不允许。

**我的倾向。** 选项一，加上"允许整数字面量进入浮点位置"。

**决定：** [ ] 选项一　[ ] 选项二　[ ] 选项三　[ ] 另议：
**整数字面量进浮点位置：** [ ] 允许　[ ] 不允许

## B2. 模块变量：既是常量又可写

**原问题（首轮第 11 条之二）。** 接着 A7。模块变量可写，又能出现在 `ConstExpr` 里。于是规范里凡是说"编译期常量"的检查，遇到模块变量都会出现"编译期的判断和运行时的事实对不上"。另外 §7.4 说赋值目标是"可写变量标识符"，却没有定义哪些变量不可写。

**规范现状。**

- §5.3："下标若为编译期常量且越界，必须编译报错。"
- §7.3.2："整数 `/` 或 `%` 的右操作数若为编译期常量 `0`，必须报编译期错误。"
- §7.4："可写变量标识符 `id`。"

**例子。**

```cy
i32 cursor  = 5;
i32 divisor = 0;
[4]i32 table = [1, 2, 3, 4];       // （数组字面量能否用于模块变量，见下文）

func main() -> void {
    cursor = 2;
    divisor = 3;
    print table[cursor];           // cursor 的初始值 5 越界 → 编译错误？运行时它是 2
    print 10 / divisor;            // divisor 的初始值是 0 → 编译错误？运行时它是 3
}
```

**选项。**

- **选项一：诊断只认"不含变量"的常量。** "编译期常量下标越界""编译期常量除零"这两项诊断，只在表达式完全由字面量、运算、转换、`.len` 组成时触发；只要出现模块变量名就按运行期值处理。模块变量保持可写。`ConstExpr`（数组长度、模块变量初始化、默认参数）仍然可以引用模块变量的初始值。
  - 好处：改动最小，没有隐藏规则。
  - 坏处：`[capacity]i32 buf` 用的是 `capacity` 的初始值，之后 `capacity` 被改写，两者不再相关。这只是容易让人误会，不会出错。
- **选项二：被 `ConstExpr` 引用过的模块变量不可写。** 一个模块变量只要在任何常量表达式里出现过，对它赋值就是编译错误。
  - 好处："常量"名副其实。
  - 坏处：变量能不能写，取决于别处有没有人把它用在数组长度里，是一种"远处生效"的规则；跨模块导入时更难看清。
- **选项三：加常量声明关键字。** 规范明确说"不新增常量声明关键字"，所以这等于推翻已定规则，我只是列出来。

**"可写变量"怎么定义。** 如果选选项一，语言里没有不可写的变量（参数是按值复制的副本，`catch` 变量、`for` 变量也都是普通变量），§7.4 的"可写"二字应当删掉。如果选选项二，"不可写变量"就是那些被 `ConstExpr` 引用的模块变量。

**【新】附带发现：类对象作模块变量无法声明。** 模块变量必须用 `ConstExpr` 初始化，而 `ConstExpr` 不允许函数调用（`Arena.init(...)` 是函数调用），类的 `{ ... }` 构造又只能出现在类内部。所以 `Arena global = ...;` 在模块顶层根本写不出来。数组字面量和 `typedef` 对象字面量算不算 `ConstExpr` 里的"字面量"，规范也没说。

- 能用的变通：`*Arena | null global = null;`，在 `main` 里指向一个 `main` 的局部变量（`main` 的栈帧活到程序结束）。
- 建议：(a) 明说"元素全为 `ConstExpr` 的数组字面量和 `typedef` 对象字面量也是 `ConstExpr`"；(b) 明说类对象作模块变量不可声明，并给出上面的变通写法。如果你想让类也能作模块变量，就需要另外设计。

**我的倾向。** 选项一，删掉"可写"二字，并采纳 (a)(b)。

**决定：** [ ] 选项一　[ ] 选项二　[ ] 另议：
**类对象作模块变量：** [ ] 接受不可声明，写明变通　[ ] 需要支持，另行设计

## B3. 窄联合能否直接赋给宽联合；联合标签怎么编码

**原问题（首轮第 12 条之四）。** `i32 | null` 的值能不能直接放进 `i32 | f32 | null` 的位置，规范没说。这还牵涉 `catch` 能接住什么。

**规范现状。**

- §4.4："将属于联合类型 `U` **成员类型**的值直接赋给期望类型为 `U` 的位置，是合法的联合构造行为。"
- §12.2："联合捕获匹配：`T_catch` 为联合类型且**包含** `T_throw`。"
- §4.1："标签与成员类型的对应在编译期确定。"
- §11.3：收窄字段"严格保留父类原始声明的……联合标签编码格式"，并且允许"将 `A | B` 收窄为成员类型或**子集联合**"。

**例子。**

```cy
typedef Small = i32 | null;
typedef Big   = i32 | f32 | null;

func find() -> Small { return null; }

Big b = find();          // Small 不是 Big 的"成员类型"（A5 展平后 Big 的成员是 i32、f32、null）

func risky() -> void {
    Small s = 1;
    throw s;             // 抛出的静态类型是 Small
}

try { risky(); }
catch (Big e) { }        // Big "包含" Small 吗？
```

**分析。** 按 §4.4 的字面，`Small` 不是 `Big` 的成员类型，所以 `Big b = find();` 是错误。要写成：

```cy
Small s = find();
Big b = null;
if (typeof(s) == i32) b = s.as(i32);
```

能写，但是啰嗦，而且每多一个成员就多一个分支。

**是否允许，取决于标签怎么编码。**

- **按联合局部编号**（每个联合类型里成员编号 0、1、2…）：同一个成员在 `Small` 和 `Big` 里编号可能不同。窄转宽需要一次标签重映射（查表或分支），这是一个隐藏的运行时动作。
- **全局类型标识**（每个类型在整个链接产物里有唯一的标识，联合标签直接存它）：`i32` 在任何联合里标签都一样。窄转宽只是原样复制，标签不用动。

**【新】两条已定规则其实已经偏向全局类型标识。**

1. **异常匹配需要它。** `throw` 和 `catch` 在不同函数里，运行时必须知道异常槽里放的是什么类型才能做"精确匹配"。也就是说异常槽里必须存一个全程序通用的类型标识。这个机制反正要有。
2. **字段收窄需要它。** 父类字段 `A | B | C` 收窄为 `A | B` 后，槽必须保留父类的标签编码。如果用局部编号，这个字段里的 `A | B` 就和别处独立声明的 `A | B` 编码不同，同一个类型有两种表示，复制出来还要重映射。用全局标识就没有这个问题。

**选项。**

- **选项一：全局类型标识，允许窄转宽。** 联合标签是全局类型标识。把成员集合是 `U` 的子集的联合值赋给 `U` 的位置，属于联合构造的一种，合法；运行时只是复制并在需要时把槽尾清零。`catch` 的"包含"按子集理解，上例两处都合法。
  - 代价：标签的宽度要能容纳全局标识（比 1 字节的局部编号大）；规范需要说明标识在一次链接内唯一，这可以比照字符串字面量"同一链接产物内共用地址"的规则来写。
- **选项二：局部编号，禁止窄转宽。** 标签是联合内的小整数，最省空间。`Big b = find();` 是错误，必须手工分支。`catch (Big e)` 接不住 `Small`。字段收窄为"子集联合"的那条需要另外补规则（这个字段的类型和独立的 `A | B` 不可互换），异常匹配另用一套类型标识。
- **选项三：局部编号，允许窄转宽。** 编译器在转换处插入标签重映射。写起来方便，但有隐藏的运行时动作，和"成本可见"的取向不太合。

**我的倾向。** 选项一。它让三处规则（联合构造、异常匹配、字段收窄）用同一个机制，没有特例。

**决定：** [ ] 选项一　[ ] 选项二　[ ] 选项三　[ ] 另议：

## B4. 字面量类型的规则

**原问题（首轮第 13 条）。** 字面量类型在规范里被多处使用，但它本身没有定义：没有文法，没有说明它和 `string`、`i32` 的关系，也没有说明它的值占多少空间。字段收窄一节整个建立在"字面量类型是原类型的子集"这个没写出来的概念上。

**规范现状。**

- §3.1："支持一般联合类型、字面量类型……"；文法里 `TypeAtom` 引用了 `LiteralType`，但没有 `LiteralType` 的产生式。
- §4.1：用"具有不同字面量字段的对象类型，例如 `kind: "user"` 与 `kind: "order"`"来区分对象种类。
- §11.3：`"user" kind;`、`200 code;`，"收窄后的类型必须属于父类原字段类型的子集"。

**例子。**

```cy
"user" tag = "user";            // 声明一个字面量类型的变量
string s = tag;                 // 合法吗？"user" 类型的值能当 string 用吗？
print tag;                      // print 接受字面量类型吗？
bool same = tag == "user";      // 能比较吗？

typedef Kind = "user" | "order";
Kind k = "user";                // "user" 这个字面量在这里是什么类型？
string name = k.as("user");     // ？

200 code = 200;                 // 200 的底层类型是什么？i32？
i32 n = code;                   // 合法吗？
```

**需要回答的问题。**

1. 哪些字面量可以作类型：字符串、整数、`true` / `false`？浮点呢？
2. 字面量表达式 `"user"` 在期望类型是 `"user"` 时，是什么类型？
3. 字面量类型的值能否用在需要其底层类型（`string`、`i32`）的地方？
4. 整数字面量类型 `200` 的底层类型是什么？
5. 字面量类型的值在内存里占多少空间？
6. `string | "user"` 归一化时，`"user"` 会被 `string` 吸收吗？

**两个整体方案。**

- **方案一：字面量类型是"只有一个合法值的底层类型"。**
  - 表示和底层类型完全相同：`"user"` 类型的值就是一个 `string` 视图（地址加长度），`200` 类型的值就是一个 `i32`。
  - 字面量表达式在期望类型是字面量类型时定型为该类型（和数值字面量按期望类型定型是同一个思路）；值不符则编译错误。
  - 字面量类型的值可以直接用在需要底层类型的位置。表示相同，所以零成本；这要作为与"联合构造"并列的第三种合法的非转换来写明。反方向（`string` 到 `"user"`）不允许。
  - 整数字面量类型的底层类型：独立使用时为 `i32`；在字段收窄里取父类字段的类型。
  - 好处：和"物理槽位保持"完全吻合（收窄字段的槽里本来就是一个 `string`）；A8 的"读取等同 `.as()`"直接成立；`print`、`==` 都自然可用。
  - 坏处：`"user" | "order"` 占"标签加 16 字节字符串槽"，槽里的内容是多余的。用带字面量字段的对象做判别联合时，`kind` 字段白占空间，因为联合标签已经能区分了。
- **方案二：字面量类型是零尺寸的单值类型。**
  - 值不占空间，类型本身就说明了值。`"user" | "order"` 只有一个标签，相当于 C 的枚举。
  - 用在需要 `string` 的位置时，编译器当场给出那个常量字符串。
  - 好处：判别联合没有冗余；可以当枚举用。
  - 坏处：在收窄字段里，槽是父类的 `string` 槽，子类"读取"这个零尺寸类型时不读槽，直接得到常量。这等于编译器假设了"槽里一定是 `"user"`"，和 A8 以及附录 B 的立场有冲突，需要专门解释。实现也更复杂。

**我的倾向。** 方案一。它规则少、和已定的槽位保持规则一致，冗余空间是可以接受的代价。同时建议：字面量类型只支持字符串、整数和布尔，不支持浮点；`string | "user"` 归一化为 `string`。

**决定：** [ ] 方案一　[ ] 方案二　[ ] 另议：

## B5. 对收窄字段取地址，得到什么类型的指针

**原问题（首轮第 15 条之二）。** 收窄字段的静态类型和它所在槽的物理格式不一样。`&user.value` 的类型没有规定。

**规范现状。** §11.3：槽"严格保留父类原始声明的槽位大小、对齐、偏移量及联合标签编码格式"；"通过子类写入该字段时自动维护对应成员标签并执行第 4 章的尾部清零"。

**例子。**

```cy
class Entity { i32 | null value; }
class User extends Entity { i32 value; }

func set(*i32 target) -> void { target.* = 7; }

func demo(User user) -> void {
    set(&user.value);        // &user.value 是 *i32 吗？
    // 如果是：set 只写了 4 个字节，没有更新标签。
    // 父类代码随后读这个槽，看到的标签可能还是 null。
}
```

**选项。**

- **选项一：指针类型取父类的原始字段类型。** `&user.value` 的类型是 `*(i32 | null)`。它如实反映槽的物理格式；通过它写入会走联合写入规则，标签自动维护。上例 `set(&user.value)` 是类型错误，作者被迫正视"这其实是个联合槽"。
- **选项二：指针类型取收窄后的类型。** `&user.value` 是 `*i32`，指向槽里存放成员值的位置。通过它写入不维护标签，一致性由作者负责。
- **选项三：禁止对收窄字段取地址。**

**我的倾向。** 选项一。它不隐藏任何东西，也不需要新增禁令。对字面量收窄（`"user" kind`）同理，`&user.kind` 是 `*string`。

**决定：** [ ] 选项一　[ ] 选项二　[ ] 选项三　[ ] 另议：

## B6. `super.method(...)` 怎么传接收者，以及接收者的几个附带问题

**原问题（首轮第 16 条之三、之四）。** `super.method(...)` 的参数里要不要写接收者，规范没说。字段和方法能不能同名，也没说。

**规范现状。**

- §11.5：`SuperCallExpr = "super", ".", Identifier, "(", [ Arguments ], ")";`，"子类在自身方法内部可通过 `super.method(...)` 显式调用直接父类的对应方法实现"。
- §11.4："接收者显式写为首参数 `Circle self`。"
- 【新】保留字表（§2.2）里**没有** `self`，所以 `self` 只是一个普通的参数名。

**例子。**

```cy
class NamedCircle extends Circle {
    string name;

    func area(NamedCircle self) -> f64 {
        return super.area() * 2.0;               // 写法一：接收者自动传入
        // return super.area(Circle(self)) * 2.0; // 写法二：接收者显式写出
    }
}
```

**先指出一个事实。** 由于分派是静态的，`Circle(self).area()` 本身就会调用父类的实现。所以 `super.area()` 在语义上只是它的简写，并没有带来新能力。

**选项。**

- **选项一：自动传入。** `super.m(args)` 定义为 `Parent(接收者).m(args)` 的简写，"接收者"是当前方法的首参数。
  - 写起来短。需要先把"接收者参数"定义清楚（见下）。
- **选项二：显式传入。** `super.m` 只是父类那个函数的名字，所有参数（含接收者）都要写：`super.area(Circle(self))`。
  - 完全显式，不依赖"当前接收者"这个概念。但比直接写 `Circle(self).area()` 还长，`super` 几乎没有存在的必要。

**附带问题（建议一并定下）。**

1. **每个方法都必须有接收者吗？** §11.5 说方法指针"统一为以显式接收者为首参数"，暗示是。建议：除 `init` 外，类的方法的首参数必须是该类的对象；没有接收者的"关联函数"不支持，写成普通模块级函数。
2. **接收者必须叫 `self` 吗？** `self` 不是保留字。建议：名字不限，`self` 只是惯例；或者把 `self` 加入保留字并强制使用。两者都行，你选。
3. **字段和方法能否同名？** 字段可以是函数指针，`obj.f(x)` 既可能是"调用方法 `f`"，也可能是"调用字段 `f` 里存的函数指针"。所以同名必须是错误。建议：一个类的字段和方法（含继承来的）共用一个名字空间，重名报错；子类覆写方法、收窄字段是仅有的两种"同名再声明"。

**我的倾向。** 选项一；每个方法必须有接收者；`self` 不保留、名字不限；字段与方法同名报错。

**决定：** [ ] 选项一　[ ] 选项二　[ ] 另议：
**接收者名字：** [ ] 不限　[ ] 保留并强制 `self`
**字段与方法同名：** [ ] 报错　[ ] 另议：

## B7. 把"没有未定义行为"这件事补全

**原问题（首轮第 14 条）。** 规范在联合读取、除零、整数溢出上都明确选择了"有确定结果，编译器不得假设它不发生"。但这个立场有几个口子没有堵上。跨成员读取和任意指针转换都合法，意味着任何类型的位置上都可能出现任意的位模式；另外几种运算在 LLVM 里默认是"未定义"的，规范不写明，实现就会把未定义行为漏进来。

**规范现状。**

- §4.3：成员不匹配的读取"不构成未定义行为"，编译器"不得以此删除代码或改变结果"。
- §7.3.2：除零"不是未定义行为"，Trap；整数溢出回绕。
- §5.3：不采用严格别名假设。

**需要逐项定下的情形。**

| 情形 | 例子 | 可选定义 | 我的倾向 |
| --- | --- | --- | --- |
| `bool` 的字节不是 0 或 1 | `(i32 \| bool)` 存入 `2` 后 `.as(bool)` | (a) 非零即真；(b) 只看最低位 | (a) |
| 移位量为负或不小于位宽 | `i32 x = 1 << n;`，`n` 为 40 | (a) 移位量按位宽取模；(b) 结果为 0 或符号位填充；(c) Trap | (a)，一条按位与指令，通常免费 |
| `>>` 对有符号数 | `-8 >> 1` | 算术右移（有符号）与逻辑右移（无符号） | 写明即可，规范目前没写 |
| 浮点转整数，值超范围或是 NaN | `i32(1e20)`、`i32(nan)` | (a) 饱和到最大或最小值，NaN 得 0；(b) Trap | (a)，与"浮点不额外插入运行时检查"一致 |
| 整数转更窄的整数 | `i8(300)` | 截断保留低位 | 写明即可 |
| 整数转浮点、`f64` 转 `f32` | `f32(16777217)` | 就近舍入到偶数 | 写明即可 |
| 指针与整数互转用哪种整数 | `u64(ptr)`、`*T(addr)` | (a) 只允许 `u64`；(b) 任意整数，按需截断或零扩展 | (a)。规范里 `.len` 是 `i64`，已经隐含 64 位地址 |
| 联合的标签不是任何成员 | 通过指针把标签写坏 | `typeof(x) == T` 对所有 `T` 都为假 | 写明即可，自然成立 |

**更大的一个问题：无效内存访问算什么。** 规范说内存寿命、边界、指针有效性"由作者负责"，但没有说作者没尽到责任时程序处于什么状态。有两种定法：

- **定法一：行为由目标平台决定，但编译器不得利用。** 越界读写、读已释放的内存，结果是平台上实际发生的事（读到别的数据、段错误等）；编译器不得以"这种访问不会发生"为前提删除或改写代码。这和除零那条"编译器不得假设除数必不为 0"是同一个态度。实现上要求后端不使用相应的优化假设。
- **定法二：完全不作规定。** 一旦发生，程序的任何行为都不受规范约束。这就是 C 的未定义行为。

规范目前的文字读起来更像定法一，但没有明说。建议在 §1.2 用一小段把三类行为分清楚：有确定结果的、Trap 的、由平台决定但编译器不得利用的。

**决定：** 表格各项 [ ] 全部按倾向　[ ] 逐项另议：
**无效内存访问：** [ ] 定法一　[ ] 定法二

## B8. 普通代码能否构造字符串、取得类型尺寸

**原问题（首轮第 17 条）。** 规范把字符串拼接、动态数组、Arena 都交给"库"实现，但没有给库作者提供做这些事所必需的手段。

**规范现状。**

- §6.2："排序与拼接由普通函数完成。"
- §1.1："手工分配、Arena、引用计数容器由库通过普通类型、函数和方法表达。"
- §11.2：`sizeof(Parent)` "仅用于规范描述尺寸"，"该记号不新增语言运算符"。
- §13.2："操作系统基础能力由编译器内部运行时原语提供给基础库。"
- 附录 B："本文不由此要求新增布局反射或对象建立机制。"

**例子一：拼接函数写不出来。**

```cy
func concat(*Arena arena, string left, string right) -> string {
    *u8 buffer = arena_alloc_bytes(arena, left.len + right.len);
    // …逐字节复制 left 和 right…
    return ???;      // 手里有地址和长度，怎么变成 string？
}
```

没有任何语法能从"地址加长度"得到一个 `string`。反方向也一样：拿不到字符串的地址，只能 `s[i]` 一个字节一个字节读。

**例子二：分配器不知道该分配多少。**

```cy
func arena_alloc_node(*Arena arena) -> *Node {
    return *Node(arena_alloc_bytes(arena, ???));   // Node 占多少字节？
}
```

目前唯一的办法是技巧：`*Node zero = *Node(0); u64 size = u64(&zero[1]);`。

**【新】相关的一个空白。** 取地址 `&` 能作用于哪些表达式，规范没有写。合理的推导是"只能作用于存储位置"。但 `&s[0]`（字符串的首字节）算不算？如果允许，就得到一个能写只读字符串的 `*u8`。

**选项。**

- **选项一：保持现状。** 这些能力只通过编译器内部原语提供给基础库；用户代码需要时调用基础库。用户自己写容器时只能用技巧。规范应当明说这是有意为之。
- **选项二：加最小的内建能力。**
  - `sizeof(DeclType)`，结果是编译期常量；参数既可以是类型，也可以是类名（`sizeof(Node)` 正是分配器最需要的）；
  - 从地址和长度构造字符串，例如 `string(pointer, length)`；
  - 取字符串的地址，例如 `s.ptr`，类型为 `*u8`（与已有的 `s.len` 对称）。
  - 这三样都不引入隐式行为，和"显式内存"的定位一致。因为语言没有泛型，每个容器都要按具体类型手写，`sizeof` 的需求会反复出现。
- **选项三：把字符串的布局写成规范。** 规定 `string` 的内存布局等同于某个具体的两字段结构，作者通过指针转换来构造。不加语法，但把一个实现细节固定成了语言规则。

**我的倾向。** 选项二。同时规定 `&` 只能作用于存储位置，`&s[i]` 不允许（要地址用 `s.ptr`）。

**决定：** [ ] 选项一　[ ] 选项二　[ ] 选项三　[ ] 另议：

## B9. 异常：没人接、槽多大

**原问题（首轮第 18 条之一、之三）。** 异常一路传播到 `main` 之外会怎样，规范没写。异常槽的容量完全由实现决定，导致"同一个程序换个编译器可能编译不过"。

**规范现状。**

- §12.2："目标平台的固定异常槽容量由实现约定记录。"超过容量是编译错误。
- §12.3："若异常未匹配……该清理语句并不保证执行。"但没有说最终没人接会怎样。

**例子。**

```cy
func main() -> void {
    throw 42;                  // 没有任何 try
}

typedef Report = { detail: [64]u8, code: i32 };   // 68 字节（对象类型文法只是示意）
func fail(Report r) -> void { throw r; }          // 能编译吗？取决于实现
```

（原例抛的是类对象，按 A1 的决定已不合法，改成了 `typedef` 结构对象。）

**A1 决定带来的一个后果。** 类对象只能以指针形式抛出，而栈展开会销毁抛出点的栈帧：

```cy
func fail() -> void {
    Failure f = Failure.init(3);
    throw &f;              // 合法，但 catch 拿到的是悬空指针
}
```

被指对象必须放在 Arena 或模块变量指向的存储里。§12.1 已经说了"异常值中的指针不延长所指数据的寿命"，建议在那里加上这个例子。

**需要定的三件事。**

1. **未捕获的异常。** 最自然的定法是"等同于 Trap，立即终止进程"，和整数除零用同一个机制；退出状态由实现记录。
2. **槽容量。** 可选：
   - (a) 规范给一个保证下限（例如"不小于 N 字节"），实现可以更大；
   - (b) 比照 §13.1 的嵌套深度，规范给默认值并规定可以用编译器参数调整；
   - (c) 保持完全由实现决定。
3. **【新】异常槽里必须带类型标识。** `throw` 和 `catch` 在不同函数里，运行时要靠槽里记录的类型标识做匹配。规范应当写明这一点（它是 B3 的依据之一）。

**我的倾向。** 未捕获即 Trap；容量按 (b)，给默认值加编译器参数；写明槽内带类型标识。

## B10. "所有路径都返回值"按什么规则判定

**原问题（首轮第 19 条）。** 规范要求"存在正常执行到末尾而未返回值的路径时必须编译报错"，但没有给出判定规则。不同的实现会对同一个程序给出不同的结论。

**规范现状。** §10.2："上述要求针对正常执行到末尾的路径，不要求异常传播或永不结束的路径凭空产生返回值。静态分析的实现须满足这里的返回约束。"

**例子。**

```cy
func a() -> i32 { while (true) { } }                           // 永不结束。合法吗？
func b(i32 x) -> i32 { if (x > 0) return 1; else throw x; }    // 两个分支都不落到末尾
func c() -> i32 { for (;;) { if (ready()) return 1; } }        // 只能从 return 出去
func d(bool f) -> i32 { if (f) return 1; if (not f) return 2; }// 逻辑上必返回，但要推理才知道
func e(i32 x) -> i32 { while (x > 0) { return 1; } }           // 循环可能一次都不进
```

**建议的规则（保守的语法判定，不做数值推理）。** 定义"语句能否正常结束"：

- `return` 和 `throw` 不能正常结束。
- 块：其中任何一条语句不能正常结束，则块不能正常结束。
- `if` 带 `else`：两个分支都不能正常结束时，才不能正常结束。不带 `else` 的 `if` 总能正常结束。
- `while`：条件是字面量 `true`，并且没有以它为目标的 `break` 时，不能正常结束；否则能。
- `for`：条件省略或是字面量 `true`，并且没有以它为目标的 `break` 时，不能正常结束；否则能。
- 具名块或具名 `if`：有以它为目标的 `break` 时，能正常结束。
- `try / catch`：`try` 块和 `catch` 块都不能正常结束时，才不能正常结束。
- 其他语句（包括任何函数调用）都能正常结束。

有返回值的函数，如果函数体"能正常结束"，就报错。

**按这个规则。** `a`、`b`、`c` 合法；`d` 和 `e` 报错（`d` 需要作者在末尾补一个 `return`）。

**一个子问题。** `return` 之后还有代码（不可达代码）要不要报错？建议不报。

**决定：** [ ] 采用上述规则　[ ] 另议：

## B11. 较小的几项

### B11a. 导入：重名、循环、带不带方法

**原问题（首轮"较小的问题"之一）。**

**规范现状。** §9.1：`import { a, b } from module;`，导入的名字直接进入本模块的名字空间；类型、变量、函数共用名字空间。

**例子。**

```cy
import { init_all } from graphics;
import { init_all } from audio;        // 重名，无解
import { Circle } from shapes;         // Circle 的方法和外部 impl 跟着来吗？
```

**建议。**

1. **重命名。** `as` 已经是保留字，可以直接用：`import { init_all as init_audio } from audio;`。不加限定访问（`audio.init_all`），保持简单。
2. **类的方法随类导入。** 方法和外部 `impl` 没有独立的名字，不可能单独导入，所以导入类就必须带上它的全部方法。这其实可以推出，写明即可。
3. **循环导入。** 模块没有顶层执行，声明又是全模块收集后再绑定，所以 A 和 B 互相导入对函数和类没有害处。建议允许，只对两种真正的循环报错：模块变量的常量初始化互相依赖；类的继承关系成环。（原来这里还列了"类按值互相包含导致尺寸无穷"，按 A1 字段不能是类对象，这种情况不存在了。）
4. **导入的模块变量。** 导入引用的是原声明身份，所以导入方对它赋值，改的就是原变量。写明即可。

**决定：** [ ] 全部按建议　[ ] 逐项另议：

### B11b. 默认参数的位置

**原问题（首轮"较小的问题"之一）。** `init` 可以有默认参数，但没说默认参数能不能出现在中间，也没说调用时怎么省略。

**建议。** 带默认值的参数必须排在所有不带默认值的参数之后；调用时只能从末尾开始省略。

**决定：** [ ] 确认　[ ] 另议：

### B11c. 递归的 `typedef`

**原问题（首轮"较小的问题"之一）。** `typedef` 能不能引用自己，没有规定。

```cy
typedef List = { value: i32, next: *List | null };   // 经由指针引用自己
typedef Bad  = Bad | i32;                            // 直接引用自己
```

**分析。** 别名是透明的，结构兼容要靠展开来比较。一旦允许递归，"展开"不会终止，比较两个递归别名是否结构相同需要专门的算法。类不参与别名展开和结构兼容（A1），没有这个问题。

**建议。** `typedef` 不得直接或间接引用自己；需要递归的数据结构用 `class`（`class Node { *Node | null next; }`）。

**决定：** [ ] 确认　[ ] 另议：

### B11d. 十六进制字面量、`\xNN` 转义、字符字面量

**原问题（首轮"较小的问题"之一）。** 语言主打字节和位操作，但数值字面量只有十进制，字符串里也没有写任意字节的办法。

**规范现状。** §2.2 只定义了十进制整数和十进制小数。§2.3 的转义只有 `\n \r \t \0 \\ \"`。§2.1 说"字符串和注释允许 UTF-8"，同时又说内容字节"按原值保留"。

**例子。**

```cy
u32 mask = 4294901760;            // 想写 0xFFFF0000
u8 escape = 27;                   // 想写 0x1B
string header = "...";            // 想放一个 0xFF 字节，没有办法
```

**需要定的事。**

1. 是否加十六进制整数字面量 `0x...`（以及是否顺便加二进制 `0b...`、数字分隔符 `_`）。
2. 是否加 `\xNN` 转义。
3. 是否加字符字面量 `'a'`（类型为 `u8`）。
4. 源文件字符串里出现不合法的 UTF-8 字节序列：是报错，还是按原值保留？这两句话现在的读法不一致。

**我的倾向。** 加 `0x` 和 `\xNN`，这两样对一门系统语言接近必需。字符字面量和 `0b`、`_` 可以暂缓。不合法的 UTF-8 按原值保留，因为规范的立场是"字符串是字节序列，语言不解释编码"。

**决定：** `0x`：[ ] 加 [ ] 不加　`\xNN`：[ ] 加 [ ] 不加　字符字面量：[ ] 加 [ ] 暂缓
**不合法 UTF-8：** [ ] 按原值保留　[ ] 报错

## C2. 示例里的类都没有 `init`；类内构造限制的理由没写

**原问题（首轮"较小的问题"之一）。** 规范规定类实例只能通过 `init` 或类自身的方法产生（§11.6：类外禁止 `{ ... }` 构造）。但所有示例里的类（`Circle`、`Rect`、`Node`、`Counter`）都没有 `init`，按规范这些类在外部一个实例都造不出来。

另外，这条限制可以被绕过：字段全部公开，所以拿到一块内存后可以逐字段写。

```cy
*Node node = *Node(arena_alloc_bytes(&arena, 4));
node.*.id = 42;          // 没有经过 init，也没有用 { ... }
```

`examples/memory-and-exceptions.md` 里的 `arena_alloc_node(&arena, 42)` 大概就是这么实现的。

**问题。** 既然能绕过，这条限制想保护什么？我的理解是：它保证"以值的形式凭空出现的类实例"一定经过类自己的代码，从而每个字段都被显式赋过值；它不是访问控制。如果是这个意思，建议在 §11.6 写一句说明，免得读者把它当成封装机制。

**处理。** (1) 给示例里的类补上 `init`，并展示构造调用；(2) 在规范里补一句限制的目的。

**决定：** [ ] 按上述处理　[ ] 另议：

## C3. 没有字段的类无法构造

**原问题（首轮 C 组清理项）。** `ClassDecl` 允许类体为空，但 `ObjectLiteral` 的文法要求至少一个字段，所以空类的 `init` 里写不出 `return { };`。（`SuperInitExpr` 的文法倒是允许空的 `{ }`。）空类的尺寸也没有规定。

**处理。** 二选一：允许类内构造使用空的 `{ }`，并规定空类尺寸为 0；或者禁止没有字段的类。

## C5. 建议：位运算优先级提到比较之上

**原问题（首轮第 5 条）。** §7.1 把 `&`、`^`、`|` 放在相等比较之下，沿用了 C 的做法。这是规范已定的规则，以下只是建议。

**例子。**

```cy
if (flags & mask == 0) { }      // 解析为 flags & (mask == 0)
```

**先说一个对你有利的事实。** 在 Cyly 里这个写法**不会**悄悄出错：`mask == 0` 是 `bool`，`i32 & bool` 没有定义，所以它是编译错误。C 里的那个经典陷阱在这里被类型系统挡住了。所以这一条纯粹是书写便利问题：现在每次都必须写 `(flags & mask) == 0`。

**建议。** 把按位与、异或、或三层移到大小比较之上（Go、Rust、Swift 都是这样）。如果你更看重"和 C 的优先级表一致"，保持不动也完全没问题。

**决定：** [ ] 提到比较之上　[ ] 保持现状

## C6. 建议：README 的措辞与排序布局不一致

**原问题（首轮第 3 条）。** README 第一段说 Cyly"保留 C 对内存布局和运行成本的直接控制"。但规范规定类和 `typedef` 对象的字段一律按"对齐从大到小、再按字段名字典序"重排（§3.4、§11.2），作者不能决定字段顺序。

**这意味着什么。** 作者无法让一个类的布局对上某个二进制格式（网络包头、文件头），也无法手工把常用字段排在一起。读写这类格式只能逐字节手工编解码。

**我的理解。** 排序布局是为了让"字段集合相同的 `typedef` 对象布局一致"，这对结构兼容是必需的；对 `class` 则不是必需的（类不参与结构兼容，A1），只是为了规则统一。这是规范已定的规则，我不建议现在动它。

**处理。** 只改 README 的措辞，把"直接控制内存布局"改成"可预测的内存布局"之类。中英文两份都要改。

**决定：** [ ] 改 README 措辞　[ ] 保持　[ ] 想重新考虑 `class` 的布局规则
